## 结论

1. 三态判定本身写对了（probe 抛/归 unreachable、粘性、fail-closed 初值），但**唯一的消费点被折叠回二态**：`isInitSurfaceOpen()` 零生产调用点，守卫只看 `isSystemInitialized()`，于是"unreachable 期间初始化入口仍可能开放"这条链并没有真正关闭。
2. 更危险的是 DSM 的默认策略：`dropTablePolicy='always'` 且`init-dsm` 不传参 → **每次启动都会 DROP 掉 schema 之外的表与列**，而备份的"是否需要"在两个文件里被解读成相反默认、备份失败还可继续。
3. 其余为语义漂移类：`system_type` 三值（'hidns'/'hidns-dsm'/'hidns-migration'）使"遗留库"判定恒为真；连接测试与 `isSchemaInitialized` 把异常压成正常值，为上述破坏性路径提供了错误输入。

## 逐条详情

### A-1 · P0 · 协调器默认销毁未知表/列，且启动必跑

**位置**：`server/src/db/dsm/schema-reconciler.ts:434`、`server/src/db/dsm/schema-reconciler.ts:867-877`；调用点 `server/src/db/dsm/init-dsm.ts:28`

**代码摘录**：
```ts
const { dryRun = false, dropTablePolicy = 'always', forceBackup = true } = options;
```
```ts
log.warn( `Dropping obsolete column: ${tableDef.name}.${existingCol.name}` );
await this.dropColumn(tableDef.name, existingCol.name);
```

**为什么是隐性问题**：默认值语义反了。根规范反复强调「默认拒绝 + 显式豁免」，而这里是「默认允许删除」。`init-dsm.ts:28` 调 `reconcile(COMPLETE_SCHEMA, { dryRun })`，只传 dryRun，于是每次启动都等价于 `dropTablePolicy='always'`：`syncTablesDeletion` 会把数据库里所有不在 `COMPLETE_SCHEMA` 中的表 `DROP TABLE`（`schema-reconciler.ts:589-615`），`syncColumns` 会把每张已有表里所有不在声明中的列 `DROP COLUMN`（`867-877`）。两者都只留一条 `log.warn`，没有清单、没有干跑、没有二次确认，且发生在 `server.listen()` 之前。同一路径还被 `app.ts:848` 的 5 秒重连循环反复调用。

**影响**：谁会踩到——①运维为排障或报表在库里手工建的表/列；②回滚到旧版本时，新版本新增的列被当作"obsolete"删除（列里的数据随之消失）；③同一 MySQL schema 下共存的其它应用的表；④任何"条件函数写错一次"的迁移，配合 A-5 的"每次启动都判 legacy"会被反复执行。后果是不可逆的数据丢失，且日志只有一行 warn，事后难以归因。

**修复方向**：`dropTablePolicy` 默认改为 `'never'`（或 `'dry-run-only'`），删除表/列必须显式 opt-in（`DSM_ALLOW_DROP=1` + 逐项白名单）；`initializeDSM` 显式传 policy；把"将删除 N 表 / M 列"作为启动阻断条件，需 `--force-drop` 才继续。

**级别**：P0 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-2 · P0 · 初始化标记：路径与数据目录脱钩，写盘失败静默

**位置**：`server/src/service/systemState.ts:24-26`、`28-34`、`36-45`、`108-112`

**代码摘录**：
```ts
return process.env.HIDNS_INIT_MARKER || path.resolve(process.cwd(), 'data', '.initialized');
```
```ts
} catch (error) {
  log.error('Failed to write initialization marker', { error });
}
```

**为什么是隐性问题**：两个"数据在哪"的判定各写一套。数据库文件由 `dal/config.ts:124-148` 的 `resolveDefaultDbPath()` 按四级优先级解析（`DB_PATH` → `HIDNS_DATA_DIR` → SEA/pkg 的 APPDATA/XDG → `{cwd}/data`），而标记文件固定 `{cwd}/data/.initialized`。打包二进制从快捷方式/开始菜单启动时 cwd 常是 exe 目录甚至 `C:\\Windows\\System32`，标记会写到与数据目录无关、甚至不可写的位置。而 `writeMarker()` 把写入失败吞成一条 log，`markInitialized()` 返回 `void`——调用方（`routes/init.ts:365`）无法区分"已落盘"与"仅内存"。

**影响**：整套"数据库故障期间不得重开初始化入口"的防线只靠这个文件存在。触发条件是两个事实同时成立：标记丢失（写盘失败 / cwd 变化 / HIDNS_DATA_DIR 部署）+ 数据库可达但为空（被恢复成空库、或 DB 配置被改指向新库）。此时 `probeDbInitialization()` 返回 `uninitialized`，`isInitSurfaceOpen()` 为真，安装向导重新开放，首个访问者可创建管理员——正是 `root.ai.md:485` 明令禁止的场景。

**修复方向**：`markerPath()` 改为跟随数据库文件目录（`path.join(path.dirname(resolveDefaultDbPath()), '.initialized')`，`HIDNS_INIT_MARKER` 仍可覆盖）；`writeMarker()` 改为 `throw` 或返回 boolean，`markInitialized()` 返回 `{ persisted: boolean }`，落盘失败升级为 error 并在 `/api/init/status` 暴露 `markerPersisted:false`。

**级别**：P0 ｜ **归属**：后续引入（61b1078「初始化标记落盘」）｜ **置信度**：HIGH（代码事实；影响链需上述两条件同时成立）

### A-3 · P1 · 备份开关两处相反默认 + 备份结果不可区分

**位置**：`server/src/db/dsm/backup-manager.ts:16`、`39-43`、`49-53`；`server/src/db/dsm/schema-reconciler.ts:451-461`

**代码摘录**：
```ts
this.isBackupRequired = process.env.DSM_BACKUP_REQUIRED !== 'false';
```
```ts
const continueOnFail = process.env.DSM_BACKUP_REQUIRED !== 'true';
```

**为什么是隐性问题**：同一个环境变量被两个文件解读成**相反默认**——备份器认为"未设置 = 必须备份"（缺工具就 throw），协调器认为"未设置 = 可跳过"（catch 后继续）。更关键的是 `createBackup()` 在"SQLite 文件不存在"或"工具缺失且非必须"时 `return ''`，而成功时返回的是路径；`schema-reconciler.ts:451` 直接丢弃返回值，所以"没备份"与"备份成功"在调用点完全同形，无法区分。

**影响**：默认部署下若 `mysqldump` 不在 PATH：BackupManager 先 throw → 协调器 catch → `DSM_BACKUP_REQUIRED` 未设为 'true' → 打印 "continuing with reconciliation..." → 照常执行 A-1 的删除动作。用户以为 `root.ai.md:73` 说的"协调前自动备份"成立，实际一次都没备。反向组合（`=true`）才会阻断，而这恰恰不是默认值。

**修复方向**：把开关收敛到单一处（如 `dsm/constants.ts` 导出 `isBackupRequired()`）；`createBackup` 改为 `Promise<{ ok: boolean; path?: string; skippedReason?: string }>` 或直接 throw；协调器在 `!ok` 时默认中止（与"备份失败即中止"的日志文案一致）。

**级别**：P1 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-4 · P1 · 备份目标与凭据自建一套解析，与实际连接配置不一致

**位置**：`server/src/db/dsm/backup-manager.ts:39-44`、`55-56`、`68-69`；对照 `server/src/db/dal/config.ts:124-148`

**代码摘录**：
```ts
const dbPath = process.env.DB_PATH || './data/hidns.db';
if (!fs.existsSync(dbPath)) { log.warn('SQLite database file not found, skipping backup.'); return ''; }
```

**为什么是隐性问题**：备份器自己重新回答"数据库在哪、用哪个账号"，与 `resolveDefaultDbPath()`（`DB_PATH`/`HIDNS_DATA_DIR`/SEA 目录/XDG 四级）以及 `applyDatabaseConfig(config)` 传进来的显式配置都无关。默认值还三处不一致：`root.ai.md:326` 写"默认 `./HiDNS.db`"，`dal/config.ts:147` 返回 `{cwd}/data/hidns.db`，这里又硬编码 `'./data/hidns.db'`。

**影响**：走 `HIDNS_DATA_DIR`、二进制安装、或初始化向导里填了显式路径的实例，备份永远 `existsSync` 失败 → 静默 `return ''`（见 A-3：调用方当成功）→ 协调继续。MySQL/PG 同理：`DB_*` 未被写进 env 时（例如仅通过 `applyDatabaseConfig` 的显式对象连接），dump 的是 env 里的另一套目标或空库；密码经命令行传递，含特殊字符即失败。

**修复方向**：`createBackup(config: DatabaseConfig)` 接收真实配置（`getDatabaseConfig()` 或 `applyDatabaseConfig` 的入参向下传），路径统一走 `resolveDefaultDbPath()`；凭据改走 `MYSQL_PWD`/`PGPASSWORD` 环境变量或 `--defaults-extra-file`；把 `DB_PATH` 默认值以代码为准回写 `root.ai.md`。

**级别**：P1 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-5 · P1 · `system_type` 三值漂移：判定查 `hidns-dsm`，没有任何写入路径产生它

**位置**：`server/src/db/dsm/schema-reconciler.ts:37-44`；`server/src/db/dsm/migration-manager.ts:262-263`、`287-288`；`server/src/db/dsm/data-migration-runner.ts:125`、`157`、`166`；`server/src/db/dsm/schemas/complete-schema.ts:662`

**代码摘录**：
```ts
"SELECT COUNT(*) as cnt FROM schema_versions WHERE system_type = 'hidns-dsm' AND success = 1"
```
```ts
VALUES (?, ?, ?, 1, ?, 'hidns')`;
```

**为什么是隐性问题**：同一列承担三种语义：`'hidns'`（DSM 版本记录，migration-manager 写）、`'hidns-migration'`（数据迁移记录，data-migration-runner 写/查）、`'hidns-dsm'`（只出现在 `detectLegacySystem` 的判定谓词和两处 `CREATE TABLE` 的 DEFAULT 里，**没有任何 INSERT 写这个值**）。判定谓词因此恒为 0，且没有任何测试覆盖这条路径。

### A-6 · P1 · 会话级 `SET FOREIGN_KEY_CHECKS` 打在池上无效；重建迁移无事务

**位置**：`server/src/db/dsm/init-dsm.ts:204-224`（关键 215-218）；`server/src/db/dl/mysql.ts:84-96`

**代码摘录**：
```ts
await conn.execute('SET FOREIGN_KEY_CHECKS = 0');
await conn.execute('DROP TABLE dns_accounts');
```
```ts
const [rows] = await this.pool.execute(sql, params);
```

**为什么是隐性问题**：`execute` 走 `pool.execute`，每次调用从池里取一条**任意**物理连接；而 `FOREIGN_KEY_CHECKS` 是**会话级**变量。三条语句（关闭检查、DROP、恢复检查）极可能落在不同连接上，语义完全不成立。同时"建新表 → 导数据 → DROP 旧表 → RENAME"没有事务包裹。

**影响**：两种坏结果——(a) 开关没生效 → `DROP TABLE dns_accounts` 因被 `dns_records` 等表引用而报 `ER_ROW_IS_REFERENCED` → 迁移失败，但被 A-7/A-8 吞成"成功"，留下 `dns_accounts_new` 孤儿表（下次启动又被 A-1 当 ghost table 删除）；(b) 开关在某条连接上生效却再没恢复 → 该连接归还池后，后续业务写入**静默绕过外键约束**，数据完整性失守。中途失败则旧表已 DROP、新表未 RENAME，账号数据直接丢失。

**修复方向**：整段迁移放进 `transaction()` 并用同一 `trx` 执行；若必须关外键检查，在事务开始前对该连接设置并在 `finally` 恢复；或干脆改用 `ALTER TABLE dns_accounts ADD COLUMN enabled TINYINT(1) NOT NULL DEFAULT 1`（无需重建）。SQLite 分支同理，`CREATE TABLE AS SELECT` 会丢掉主键/索引/NOT NULL，应改为显式 DDL + `INSERT ... SELECT`。

**级别**：P1 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-7 · P1 · 数据迁移失败只记日志，初始化仍上报成功

**位置**：`server/src/db/dsm/init-dsm.ts:37-41`（对照同函数 46-54）

**代码摘录**：
```ts
if (result.failed.length > 0) {
  log.error( 'Some migrations failed:', result.failed.map(f => f.id));
}
```

**为什么是隐性问题**：同一函数里"完整性检查失败"会 `throw`（`init-dsm.ts:52-53`），"数据迁移失败"只 `log.error`；两者都是 void 返回，调用方无从分辨。这是"静默失败"的典型：错误被降级成日志级别。

**修复方向**：迁移失败改为 `throw new Error(...)`（或 `initializeDSM` 返回 `{ failed: string[] }`）；`initializeSchema()` 返回 `{ ok: boolean; failedMigrations: string[] }`，路由据此返回非 0 的 `code`。

**级别**：P1 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-8 · P1 · `isSchemaInitialized` 静默 catch→false，把探测失败当成"schema 未建立"

**位置**：`server/src/service/systemSetup.ts:188-194`；调用点 `server/src/routes/init.ts:318`

**代码摘录**：
```ts
export async function isSchemaInitialized(): Promise<boolean> {
  try {
    return await isDbInitialized();
  } catch {
    return false;
  }
}
```

**为什么是隐性问题**：直接违反 `root.ai.md:117`「禁止 `catch` 后静默返回 `false`」与 §数据库 9-3。注释自称"调用方在此之前已排除 unreachable"，但调用方是"先探一次 state（`routes/init.ts:310`），再调本函数（`:318`）"——两次探测之间数据库可能已经抖断；且这个 catch 连失败原因都不记录，日志里查不到。

**影响**：数据库在两次探测之间掉线 → `/api/init/admin` 返回 400 "Database not initialized. Please initialize database first."，把"数据库故障"告诉用户成"还没初始化"，引导用户去初始化一个**已有 schema** 的库；用户照做会走 `/database` 的 Scenario C（`routes/init.ts:271-297`）→ 重新 `applyDatabaseConfig` + `initializeSchema`（即 A-1 的协调器）。这正是根规范要求区分三态的初衷。

**修复方向**：删除该包装函数，让 `isDbInitialized()` 的异常直接上抛，路由把异常映射为 503（与 `state==='unreachable'` 同一分支）；若确需保留，返回 `'unknown'` 第三值而不是 `false`。

**级别**：P1 ｜ **归属**：后续引入（0f38511「区分数据库不可达与未初始化」）｜ **置信度**：HIGH

### A-9 · P1 · BAL 连接测试把查询异常变成 `success:true / hasExistingData:false`

### A-10 · P1 · BAL 的 `db` 门面用 env 推导 `type`、用"对象存在"推导 `isConnected`

**位置**：`server/src/db/bal/business-adapter.ts:25-34`；对照 `server/src/db/dal/connection.ts:322-324`、`server/src/db/dl/mysql.ts:76-82`、`server/src/db/dl/postgresql.ts:187-190`、`server/src/db/dl/sqlite.ts:77-79`、`server/src/db/database.ts:37-51`

**代码摘录**：
```ts
get type() { return process.env.DB_TYPE || 'sqlite'; },
get isConnected() { try { const conn = getConnection(); return !!conn; } catch { return false; } }
```

**为什么是隐性问题**：同一个语义（"当前连的是哪种库"、"是否连上"）在仓里有四套实现且互不一致：BAL 用**声明的** env 类型而不是 `conn.type`；BAL 的 `isConnected` 只判断 wrapper 对象是否存在（池已死也返回 true）；`ConnectionManager.isConnected` 判断 wrapper+driver；驱动层判断 `pool !== null`——而 MySQL/PG 的 `close()` 不把 pool 置空，**关闭后 `isConnected` 仍为 true**，SQLite 却置空（语义相反）。没有单一归一化点。

**影响**：(a) `getDbType()` 被 BAL 用来选择方言 SQL（如 `business-adapter.ts:2274-2279` 的 mysql/pg 分支、`2275-2279` 的反引号/双引号），一旦 env 与实际连接不一致（初始化向导中途失败、`_TEMP_DB` 内存库、测试直连、`connect(config)` 被显式调用），就会对错误方言拼 SQL；(b) `routes/system.ts:69` 的 `dbConnected` 在数据库实际不可达（池已死、wrapper 还在）时仍显示"已连接"，运维据此判断"数据库正常"。

**修复方向**：`getDbType()` 改为 `getConnection().type`；`isDbConnected()` 改为 `getConnectionManager().isConnected` 并附一次 `SELECT 1`（或直接复用 `checkHealth`）；MySQL/PG 的 `close()` 置 `this.pool = null`，使 `isConnected` 在关闭后与 SQLite 语义一致。

**级别**：P1 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-11 · P2 · `isDbInitialized` 对未知驱动类型 `return false`，被 probe 折叠为 `uninitialized`

**位置**：`server/src/db/connection.ts:65-80`（第 79 行）、`server/src/db/connection.ts:103-109`

**代码摘录**：
```ts

}
```
```ts
if (!await isDbInitialized()) return 'uninitialized';
```

**为什么是隐性问题**：三态探测的第一跳用"假"来表达"我不认识这个驱动"。`probeDbInitialization` 无法区分"users 表不存在"与"类型不认识"，后者被解释为 `uninitialized`，进而 `isInitSurfaceOpen()` 为真（初始化入口开放）。switch 没有 `default: throw`。

**级别**：P2 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH

### A-12 · P2 · DSM 版本记录谓词与写入值永不匹配

**位置**：`server/src/db/dsm/migration-manager.ts:348-355`、`330-346`、`34-40`

**代码摘录**：
```ts
WHERE semantic_version = ? AND version LIKE 'DSM-%'
```
```ts
VALUES (?, ?, ?, 1, ?, 'hidns')`;
```

**为什么是隐性问题**：`recordDSMVersion()` 先调 `recordSuccess()`（`version = this.schemaHash`，`semantic_version` = 构造函数里硬编码的 `1.5.0`），再用 `UPDATE` 把 `semantic_version` 改成 app 版本；而 `isDSMVersionRecorded()` 用 `version LIKE 'DSM-%'` 查——**任何写入路径都不会产生这种 version**，谓词恒为 false。同时 `semantic_version` 有"1.5.0 常量"与"app version"两个真相源。

**影响**：版本记录"看起来在写、实际查不到"；将来任何以 `isDSMVersionRecorded` 做门禁的迁移都会每次重跑（目前靠 `recordSuccess` 的 hash 去重侥幸不出错）；`schema_versions` 里 1.5.0 与 2.2.0 混杂，无法回答"这个库是哪一版 schema"。

**修复方向**：`recordDSMVersion` 单独 INSERT 一行 `version = 'DSM-' + appVersion`（前缀定义为常量），`isDSMVersionRecorded` 用同一常量拼接；删除构造函数里 `1.5.0` 的默认语义版本，改为必填。

**级别**：P2 ｜ **归属**：0.0.1 存量 ｜ **置信度**：HIGH
