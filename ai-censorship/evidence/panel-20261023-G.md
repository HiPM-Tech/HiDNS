- 逐点核查 `log.*` 出现在 setInterval / 轮询 / 重试 / 循环内的位置（`service/*`、`db/dal/connection.ts`、`service/taskManager.ts`）。

## 结论

1. root.ai.md §270-274 的日志限流是**强制条款**，但 logger 连一个限流原语都没有（无 throttle/once/采样），而 taskManager、NS 监控、DB 重连三处核心轮询路径都是「每迭代一条日志」，§9 实际处于**零执行点**状态。
2. 三处最关键的失败出口把错误折叠掉了：taskManager 最终失败日志只有 `err.message`（无栈）、whois/scheduler 四处错误日志连 error 对象都不传、app.ts 降级重连的 catch 完全静默 5 分钟；排障时最需要的栈恰好都不在。
3. 公共设施存在多处「同语义双实现且行为分歧」：getRootDomain（后缀表 vs 取末两段）、isValidDomain（URL 归一化 vs 标签正则）、代理类型（socks5 静默退化为 http）、env 优先级（注释/规范 vs dotenv 实际覆盖语义）。

### G-01 §9 日志限流：强制条款，零执行点（P1／与版本无关／HIGH）

位置
- `server/src/lib/logger.ts:17-27`（`SubLogger` 接口：只有 trace/debug/info/warn/error/sub/tag，没有任何限流/采样/去重 API）
- `server/src/service/taskManager.ts:251`、`:283`
- `server/src/service/nsMonitorJob.ts:131`、`:213`
- `server/src/db/dal/connection.ts:162`、`:179`、`:191`

代码摘录
```ts
// logger.ts:17-18 —— 接口里没有任何限流原语
export interface SubLogger {
  trace: (message: string, data?: unknown) => void;
// taskManager.ts:251,283 —— 每个任务开始/完成各一条 info
log.info(`Task started: ${options.name}`, { taskId, ... });
log.info(`Task completed: ${options.name}`, { taskId, duration: taskInfo.duration });
// nsMonitorJob.ts:131,213 —— 每个被监控域名每轮 2 条 info（5 分钟一轮）
log.info('Checking NS records', { domain: monitor.domain_name, monitorId: monitor.id });
```

规范条款（root.ai.md:270-274）
> 9. 日志限流（强制约束）——**同一调用点的重复日志必须限流**：在重试、轮询、冲突重排等可能高频触发的路径上，禁止每次迭代都输出一条日志。…推荐做法：仅在首次与每 N 次（或指数退避的每个量级）记录一次，并在日志中带上累计次数。…日志刷屏属于必须按 §代码审核团 上报的严重问题，不得以"日志级别可调"为由放过。

为什么是隐性问题：条款是「强制」，但代码库里 grep `throttle|rateLimit|once|sampled`（lib/、utils/）结果为 0 —— 整个项目**没有任何限流设施**，条款只能靠每个调用点自觉，而事实是没有任何调用点自觉。这不是"某处漏了限流"，而是"这条强制条款没有落点"：即使新代码想遵守，也没有可用 API，只能各写一套（或干脆不写）。

影响（可量化）
- NS 监控：`nsMonitorJob.ts:389-403` 对 N 个域名各 submit 一个任务，每任务经 taskManager 记 2 条（251/283）+ checkDomainNs 记 2 条（131/213）= **4N 行 / 5 分钟**，恒速、无上限、INFO 级别（默认可见）。N=200 时 800 行 / 300 秒 ≈ 2.7 行/秒持续输出，约 23 万行/天。失败时 `retries: 2`（396 行）再乘 3。
- DB 断连：`connection.ts:160-192` 每次尝试 3 条（162 建连、179 失败带栈、191 退避），`maxReconnectAttempts = 10`（95 行）→ 单次 connect() 最多 30 条；而健康检查每 30 秒触发一次（228 行），且 setInterval 回调是 async 无重入保护，一轮最长约 151 秒（1+2+4+8+16+30×4），**会重叠**，形成并发重连 + 日志叠加。
- `service/resource/job.ts:19-35`：采集 10 秒一轮、落库 60 秒一轮，失败即 `log.error('...', { error })`（含完整栈），持续失败时 8,640 次/天。

修复方向：在 `logger.ts` 的 `SubLogger` 上补一个限流原语（如 `log.throttled(key, msOrEveryN).warn(msg, data)`，内部按 key 维护 `{lastAt, count, suppressed}`，放行时把 `suppressed` 累计数写进 data），然后把上述三类点（任务开始/完成改为 debug 或按任务名采样、NS 监控改为仅状态非 ok 时 info、DB 重连与资源采集改为首次 + 每 N 次）接上去；taskManager 层面可只对「非周期任务」保留 info，对周期性 id 前缀降级为 debug。

### G-02 taskManager 最终失败日志丢栈（P1／存量／HIGH）

位置：`server/src/service/taskManager.ts:317-321`（对照 `:296-299`）

代码摘录
```ts
log.error(`Task failed: ${options.name}`, { taskId, attempts: attempts + 1, error: err.message });
log.warn(`Task failed, retrying (${attempts + 1}/${maxRetries}): ${options.name}`, { ..., error: err.message });
```

规范条款（root.ai.md:173）：错误日志必须包含详细错误信息（错误类型、错误消息、错误栈等），通过第二个参数 `data` 传入。

为什么是隐性问题：这里传的是**字符串** `err.message`，而不是 `err`。logger 的 `formatError()`（logger.ts:140-171）只有在收到 Error 实例时才会输出 `type` 与 `stack`；传字符串则整条链路只会打印 message。表面上"日志里有 error 字段"，实际**栈、错误类型、code、cause 全部消失**——看上去合规，读起来不可用。而 taskManager 是全系统后台任务（WHOIS、域名同步、续费、NS 监控、缓存刷新、服务监控）的**唯一失败出口**，它丢栈等于全系统后台故障都丢栈。

影响：任何后台任务失败只能拿到一句话（如 "Task timeout after 30000ms"），无法定位是哪个适配器/哪次 fetch 超时；`taskInfo.error = err`（315 行）虽保留了完整对象，但只存在内存里，进程内无日志可查。

修复方向：两处统一改为 `{ taskId, attempts, error: err }`（logger 会自动展开 type/message/stack/code）；重试那条 warn 保留 message 摘要 + 完整 error。

**同类第三处（同属 §5「失败静默」，并入本条不单列）**：`server/src/app.ts:868-875`
```ts
} catch (err) {
  retryCount++;
  if (retryCount >= MAX_RETRIES) { log.error(...); clearInterval(initCheckInterval); }
  // Still not initialized      ← 前 59 次失败一条日志都不打，err 变量未使用
}
```
数据库不可达进入降级模式后，每 5 秒重试一次、共 60 次（`MAX_RETRIES = 60`，842 行），**前 59 次完全静默**：日志里只有最初一条 "Database connection failed at startup"，之后 5 分钟内既没有"仍在重试"也没有失败原因，重连是活是死无法判断；第 60 次才打一条 `Failed to initialize after 60 attempts`。这与 §9 的"仅在首次与每 N 次记录"正好相反（应首次 + 每 N 次带累计次数），也与 §5 的"错误日志必须带上下文"相悖。附带风险（可能已由他人覆盖，若重复请合并）：`app.ts:851-862` 的恢复路径手工重列任务，缺少主路径 `startAllJobs()`（732-757）中的 `initRenewalSchedulers()`、`initWhoisSchedulers()`、`startGroupedCacheRefreshJob()` 三项，即"数据库故障后恢复"与"正常启动"两条路径启动的后台任务集合不一致。

### G-04 INFO/DEBUG 不再输出调用栈，与格式契约冲突（P1／后续引入／HIGH）

位置：`server/src/lib/logger.ts:183-184`（另 `:85`）

代码摘录
```ts
const showCaller = this.logLevel === 'trace' || entry.level === 'warn' || entry.level === 'error';
const callerStr = showCaller && entry.callerFunction && entry.callerLine ? ` [${entry.callerFunction}] [L${entry.callerLine}]` : '';
this.useColors = !noColor && (hasTTY || true);   // :85  hasTTY 判断恒真，等价于 !noColor
```

规范条款（root.ai.md:129-142）：格式为 `日期 级别 [主模块名] [子模块] [函数名] [L行号] ["标签"] 内容`；"函数名和行号由日志系统自动从调用栈捕获"；并给出 5 个示例，其中 **INFO/DEBUG 全部带 `[execQuery] [L42]`**（134-138 行）。

为什么是隐性问题：`getCallerInfo()` 在 `emit()`（288-292 行）里**无条件执行**——每次日志都构造 `new Error().stack` 并解析；然后在 `formatMessage` 里按级别**丢弃**。也就是说：默认 `HIDNS_LOG_LEVEL=info` 下，全仓 99% 的日志（info/debug）付出了抓栈开销却拿不到任何调用点信息，同时与文档写的格式和示例不一致。这不是"风格"，而是**格式契约与实现相反**：任何按文档写日志解析/告警规则（如"按 [函数名] 聚合"）的人会拿到空字段。`:85` 的 `(hasTTY || true)` 让 TTY 检测成为死代码，容器/journald 里照样输出 ANSI 转义，进一步破坏机器可解析性。

影响：默认配置下 INFO 日志无法定位来源文件行；Docker 日志中出现 `\x1b[32m` 等转义，`docker logs | grep` 与日志采集管道按级别/模块过滤需额外去色；同时每条 info 都在付 stack 捕获成本（高频路径上是纯浪费）。

修复方向：二选一——(a) 让实现服从文档：`showCaller` 恒为真（或仅 trace 之外也保留），并按级别缓存 caller；(b) 修改 root.ai.md §2 的格式与 5 个示例，明确"仅 trace/warn/error 输出调用点"。两者必须一致，不能各说一套。颜色：`this.useColors = !noColor && !!hasTTY;`（或尊重 `FORCE_COLOR`）。

### G-05 fetchWithFallback：代理失败静默改直连，语义被折叠（P1／后续引入／HIGH）

位置：`server/src/lib/proxy-http.ts:330-343`（判断入口 `:293-301`）

代码摘录
```ts
} catch (proxyError) {
  log.warn(`[${providerName}] Proxy request failed after ${proxyDuration}ms, falling back to direct connection`, {...});
  const res = await fetch(url, options);          // :339 直连，返回值与代理成功完全同形
  log.info(`[${providerName}] Direct connection successful`, { duration: `${directDuration}ms` });
  return res;
```

为什么是隐性问题：调用方传 `useProxy = true`（root.ai.md:281-282 要求 provider 必须走这条链以"适配特殊网络环境"），得到的 `Response` 与真正走了代理的 `Response` **无法区分**——没有 `viaProxy` 标记、没有 header、没有返回结构变化。于是"代理不可用"这一失败被折叠成"请求成功"：上层看到 200，就认为代理生效了。日志里虽有 warn，但 (a) 成功路径还会再打一条 `Direct connection successful`（info），(b) 调用方（provider）不读日志，无法据此决策。

影响：① IP 泄漏——用户配代理正是为了不暴露本机出口，静默直连等于把真实 IP 送给目标 API；② 结果漂移——地域/网络受限的 API 在直连下返回不同数据或超时，表现为"偶发数据不一致"，而日志里的 warn 淹没在正常流量中；③ 合规/审计视角下"配置了代理"与"实际走代理"不再等价。规范 §282 明确禁止"静默超时"，同一精神下"静默换路"更严重。

修复方向：把降级结果显式化——返回 `{ res, viaProxy: boolean, fallbackReason?: string }`（或至少设置 `res.headers['x-hidns-via-proxy']`），由调用方决定是否接受降级；对 `proxiable` 能力位（root.ai.md:304）为 true 的 provider，降级应默认**失败**而不是成功；日志侧把降级 warn 升级为 `.tag('PROXY_FALLBACK')` 并在同一调用点限流（配合 G-01）。

### G-06 代理类型静默降级：socks5 变 http（P1／存量／HIGH）

位置：`server/src/lib/proxy-http.ts:65-77`

代码摘录
```ts
if (config.type === 'socks5' && SocksProxyAgent) {
  ...
} else if (HttpsProxyAgent) {          // :71 socks5 包缺失时，落到这里
  const proxyUrl = `http://${auth}${config.host}:${config.port}`;   // :75 用 http 协议连 socks 端口
  return new HttpsProxyAgent(proxyUrl);
```

为什么是隐性问题：分支条件是 `type === 'socks5' **&&** SocksProxyAgent`。当用户配置 `type: 'socks5'` 但可选依赖 `socks-proxy-agent` 未安装/加载失败（18-23 行只 `log.warn('socks-proxy-agent not available')`，warn 级别、且是模块加载期一次性），代码会**静默走进 http 分支**，用 HTTP CONNECT 去连一个 SOCKS 端口。协议被悄悄替换，没有任何日志说明"你的 socks5 配置被当成 http 用了"。

影响：表现为"代理能创建但请求全部失败"，然后被 G-05 折叠成静默直连——用户以为代理在工作，实际既没走 socks 也没被提示。排障时会先怀疑 socks 服务器，而不是依赖缺失。

修复方向：按 `config.type` 严格分支，缺依赖时 `log.error` + 返回 null（或抛错），不得跨类型复用；启动时校验一次依赖可用性并显式标注降级状态。

### G-08 env 加载优先级与规范/注释不符（P2／存量／HIGH）

位置：`server/src/config/env.ts:34-45`

### G-11 requestLogger：每个 JSON 响应记两次，requestId 不入日志（P2／存量／HIGH）

位置：`server/src/middleware/requestLogger.ts:46-55`（另 `:21`、`:30`、`:65-67`）

代码摘录
```ts
res.send = function (data: unknown) { doLog(); return originalSend.call(this, data); };   // :46-49
res.json = function (data: unknown) { doLog(); return originalJson.call(this, data); };   // :52-55
```

为什么是隐性问题：express 4.18 的 `res.json` 结尾是 `return this.send(body)`（已在 `node_modules/express/lib/response.js` 核实），而 `this.send` 已被本中间件覆盖 → **`res.json()` 的每个响应都会触发两次 `doLog()`**（一次来自 json 覆盖，一次来自其内部的 send 覆盖）。没有 `logged` 去重标志。另外：`requestIdMiddleware`（64-69 行）生成了 `req.id` 并回写响应头，但 `doLog` 的 data 里**从不带 `req.id`**——请求 ID 这条跨切面追踪线索在服务端日志里完全缺失；`:30` 的 500 日志把 `error` 写成常量字符串 `'Server error'`，真实错误只存在于 errorHandler 的另一条日志里，两者无 requestId 关联则无法配对。

影响：日志量翻倍（每个 API 响应 2 条）；`docker logs` 里同一请求出现两行，按行数做 QPS 统计会得到 2 倍值；用户报障时提供的 `x-request-id` 在服务端日志中检索不到，只能靠时间戳猜。

修复方向：`doLog` 加 `if (logged) return; logged = true;`；`baseLog` 或 data 里带上 `req.id`；500 分支改为传 `res.locals.error`（由 errorHandler 写入）而非常量。
