## 结论

1. 最严重的隐性缺陷在 `line` 字段：它同时是"线路 ID"（阿里云）与"Cloudflare 代理开关"（`'0'`/`'1'`），而工作流动作把它硬编码成 `'0'`、更新时干脆不传——"只改值"的操作会静默把记录搬到默认线路并把 TTL 重置。
2. 任务管理器的 ID 互斥在三条路径上失效：超时（ID 已释放但任务还在跑）、`Date.now()` 生成的定时任务 ID、以及从未被读取的 `concurrency` 选项；调用方注释里"串行执行"的保证并不存在。
3. 告警链路存在系统性静默失败：`sendNotification` 返回 `void`，工作流 `notify.channel.send` 恒返回 `{sent:true}`；失败切换状态只存内存，重启后"自动回切"永久失效而状态仍报 `ok`。

## 逐条详情

### E-01（P0）`line` 字段承担两种语义，工作流把它硬编码成 `'0'`

**位置**：`server/src/workflow/actions/dns/record.ts:114`、`:194`、`:127`

**代码摘录**
```ts
// :114（dns.record.create）
const recordId = await adapter.addDomainRecord(name, type, value, '0', optionalPositiveNumber(args.ttl, 600));
// :127（dns.record.update）
const ok = await adapter.updateDomainRecord(recordId, previous.Name, previous.Type, value);
```

**为什么是隐性问题**
`DnsAdapter` 的第 4 个参数在 `DnsInterface.ts:53` 叫 `line`，但各适配器对它解释不同：
- 阿里云：`line` 是线路 ID，`'0'` = 默认线路，`'telecom'`/`'unicom'` 等是具体线路（`aliyun/adapter.ts:33-48`，`'0'` 被原样透传）；
- Cloudflare：`line` 是代理开关，`'1'`→`proxied:true`、`'0'`→`proxied:false`、其它→不传（`cloudflare/adapter.ts:433-436`，经 `buildRecordBody` 落到 `body.proxied`，`:392-393`）。

同一个字面量 `'0'` 在两种提供商里代表两件完全不同的事。而动作声明里**没有 `line` 参数**（`record.ts:24-30` 只有 domain/name/type/value/ttl），所以工作流无法表达"带代理的记录"；`update` 又直接省略该参数，落到各适配器自己的默认值：
- 阿里云 `updateDomainRecord` 内是 `Line: this.normalizeLine(line) ?? '0'`（`aliyun/adapter.ts:166`）→ **把记录从电信/联通线路搬到默认线路**；同一调用还显式传 `TTL: ttl`（:167），而 `ttl` 的默认值在阿里云是 `600`（:155）、在 Cloudflare 是 `1`（`cloudflare/adapter.ts:265`）、服务层又是 `options?.ttl || 600`（`dns-provider-service.ts:204`）。
- Cloudflare `updateDomainRecord` 走 PATCH（`cloudflare/adapter.ts:274`），`line` 缺省时 `proxied` 不被改写——同一段代码在两类提供商下后果完全不同。

**影响**
- 用户在工作流里"只改 A 记录的值"，阿里云域名下的分线路解析会被静默改成默认线路、TTL 重置为 600，无错误、无差异提示。分线路解析通常正是用户配置的核心，出错后的表现是"部分地区解析到旧 IP"，排查成本极高。
- Cloudflare 域名下工作流无法开启代理（`proxied` 被强制 `false`，与手工创建路径不一致），源站 IP 会因此直接暴露。
- 600 / 1 / 600 三个默认值分散在适配器参数、服务层、工作流动作三层，任一处单独改动都会让其余层静默失效（"默认值分散"与"字段多语义"两个反模式叠加）。

**修复方向**
在服务层建唯一归一化点，把"线路"与"代理"拆成两个显式字段，禁止调用方直接传 `line`：
```ts
// service/dns-provider-service.ts
export interface RecordSpec { line?: string; proxy?: boolean; ttl?: number; mx?: number; weight?: number; remark?: string }
// proxy → line 的映射只写一次：proxy === undefined ? line : (proxy ? '1' : '0')
```
`updateRecord` 必须先 `getDomainRecordInfo` 回读原 `Line/TTL/MX/Weight/Remark` 再原样回填，只覆盖调用方显式给出的字段；动作声明补 `line`/`proxy`/`ttl` 三个可选参数。

### E-02（P1）任务超时只"放弃等待"，却把 ID 当成已释放

**位置**：`server/src/service/taskManager.ts:265`、`:327`

**代码摘录**
```ts
const executionPromise = Promise.race([ fn(), new Promise<never>((_, reject) => { /* timeout */ }) ]);
...
this.runningTasks.delete(taskId);   // finally 内无条件执行
```

**为什么是隐性问题**
`Promise.race` 超时只让 `await` 提前返回，`fn()` 仍在执行（动作层没有任何取消机制）。但 `finally`（`:325-331`）无条件 `delete(taskId)`，于是"同 ID 只允许一个实例"这条契约在超时之后被打破：`runningTasks` 里已经没有这个 ID，下一次 `submit` 同 ID 会立刻进入 `executeTask`，与前一个仍在执行的实例并发。`:258-259` 的注释写的是"必须保证任务最终结束，否则任务 ID 永不释放"——实现只做到"释放"，没做到"结束"。

配合 `retries` 更明显：失败后 `:303-309` 用 `setTimeout` 把任务放回队首，**等待重试的这段时间任务既不在队列也不在运行集**，期间任何同 ID 提交都会被直接放行。

**影响**
- `domainSyncJob`（`timeout: 300000, retries: 1, retryDelay: 10000`，`:338-340`）与 `whois/scheduler`（`timeout: 60000`，`:69-71`）都把工作拆成"稳定 ID 的子任务"。一旦某个账户同步超时（大账户、慢 API 很常见），重试会再起一个同账户实例，两个实例同时拉取提供商域名列表并各自 `DomainOperations.update(id, {enabled: 0})`（`domainSyncJob.ts:255`）——重复的禁用写入与重复的提供商 API 调用。
- 超时任务的最终结局无人消费：它成功不会有任何记录，失败也不会；调用方只看到一条 `Task timeout`。

**修复方向**
把"结束"与"释放"绑定：超时后不要立刻删除 `runningTasks` 条目，而是标记 `status:'timed-out'` 并保留 ID 直到 `fn()` 真正 settle（`void fn().finally(() => this.runningTasks.delete(id))`）；同时给 `fn` 注入 `AbortSignal` 让适配器层可中断。短期若不实现取消，则超时后必须保留 ID（宁可让后续同 ID 提交走 deferTask 上限报错，也不要静默并发）。

### E-03（P1）`concurrency` 是死选项，调用方的"串行"注释是假的

**位置**：`server/src/service/taskManager.ts:32`、`:61`

**代码摘录**
```ts
/** 最大并发数（默认1，即串行执行） */
concurrency?: number;
...
private maxConcurrentTasks: number = 3; // 全局最大并发任务数
```

**为什么是隐性问题**
`concurrency` 只出现在类型声明里（`grep concurrency server/src/service/taskManager.ts` 仅命中 `:32`，无任何读取点）。真实并发只由全局 `maxConcurrentTasks = 3` 决定，而 `setMaxConcurrentTasks`（`:67`）全仓无调用。也就是说 8 个调用点传入的 1/3/5 全部被忽略：`groupedCacheJob.ts:61/87/100`、`recordCountCache.ts:102/119`、`domainRenewalJob.ts:230/244`、`domainSyncJob.ts:337/379/393`、`serviceMonitorJob.ts:26`、`mcpOAuthCleanupJob.ts:14`、`whois/scheduler.ts:68/176/191`、`nsMonitorJob.ts:394`。注释里的语义（"串行执行，避免并发续期"、"允许最多 5 个并发检查"）与实际行为都不符。

**影响**
- `domainRenewalJob.ts:230` 注释"串行执行，避免并发续期"，实际全局允许 3 个任务并行：初始续期与 24h 周期续期重叠时，续期请求可以并发打到同一注册商，重复续期/重复扣费的风险不再由调度器兜住。
- `serviceMonitorJob`/`nsMonitorJob` 声明 5，实际只有 3：监控项串成 3 路，慢目标会把整批拖过 5 分钟周期，进而与下一轮重叠（再叠加 E-04 的 ID 问题）。
- 任何"调大 concurrency 提速"的后续改动都不会生效，且不会有报错。

**修复方向**
二选一且必须显式：要么实现（按显式资源键计数，超限走 `deferTask`），要么从 `TaskOptions` 删除并同步改掉 8 处注释。建议实现时用 `options.group`（如 `'domain-sync'`）而非 `id` 计数，避免与"同 ID 互斥"混淆。

### E-04（P1）定时任务 ID 里塞 `Date.now()`，把互斥键变成随机键

**位置**：`server/src/service/domainSyncJob.ts:391`（同类：`domainRenewalJob.ts:242`、`recordCountCache.ts:116`、`whois/scheduler.ts:189`）

**代码摘录**
```ts
id: `domain-sync-${Date.now()}`,
```

**为什么是隐性问题**
`TaskOptions.id` 在 `taskManager` 里的唯一用途就是互斥（`:177` `runningTasks.has(id)` → `deferTask`）。这四处把时间戳拼进 ID，等于声明"每次运行都是不同任务"，互斥永久失效；而同一文件里的"首次运行"分支用的却是稳定 ID（`domain-sync-initial`、`domain-renewal-initial`、`record-count-cache-initial`、`whois-sync-initial`）。同一个语义（"这类任务同时只跑一个"）在同一文件内有两种写法。

**影响**
以 `whois/scheduler.ts` 为例：每 1 小时触发、整批超时 5 分钟，但每轮会为**每个域名**提交一个子任务（`whois-${d.id}`，稳定 ID），而全局并发只有 3（E-03）。域名上百时单轮必然超过 1 小时 → 上一轮还在跑，下一轮又整批入队，同域名的子任务全部走 `deferTask`，60 次上限后以 `Task abandoned` 失败。日志里会出现成片 abandoned，而"每小时一次"的语义从未成立。

**修复方向**
ID 只表达"哪一类任务"，不带时间：`'whois-sync'` / `'domain-sync'` / `'record-count-cache'`。需要区分轮次时放到 `name` 或新增的 `runId`（仅用于日志与运行记录，不参与互斥）。

### E-05（P1）缓存增量更新任务的 ID 同样被打散，落在读-改-写上就是丢更新

**位置**：`server/src/service/groupedCacheJob.ts:59`、`:41-53`

**代码摘录**
```ts
id: `grouped-cache-update-${cacheType}-${userId}-${change.type}-${Date.now()}`,
...
const cached = await getCachedGroupedData(userId, cacheType);   // 读
```

**为什么是隐性问题**
`updateCachedList`（`:41-54`）是典型的 read-modify-write：读整份列表 → `filter`/`map`/`push` → 整份写回。作者显然想用任务 ID 让"同一用户同一缓存类型"串行（否则不会把 `cacheType`/`userId`/`change.type` 拼进去），但末尾的 `Date.now()` 让两个几乎同时到达的变更拿到不同 ID，于是可以并发：都读到同一份旧数据、各改一处、后写者覆盖前写者。`bumpCacheVersion()` 也会被调用两次，版本号前进两次而内容只保留一份。

**影响**
前端域名/账号分组列表在"连续两次写操作"后出现条目缺失或旧值（表现为刷新后数据回退，直到 30 分钟全量刷新才恢复）。因为发生在缓存层，没有任何报错，用户只能感知"偶发数据不对"。

**修复方向**
去掉 `Date.now()`，并给该缓存键加进程内串行化：id 取 `grouped-cache-update-<cacheType>-<userId>`（同一用户同一类型天然串行，不同 `change.type` 排队而不是并发）。更稳妥的是把整份读-改-写换成数据库侧的 JSON 局部更新。

### E-06（P1）`enabled` 一个语义五种归一化，`!== false` 让禁用账户继续被同步

**位置**：`server/src/service/domainSyncJob.ts:322`

**代码摘录**
```ts
const activeAccounts = accounts.filter((acc: any) => acc.enabled !== false);
```

**为什么是隐性问题**
`dns_accounts.enabled` 在 schema 里是 `{ name: 'enabled', type: 'integer', defaultValue: true }`（`complete-schema.ts:68`），落库为 `0`/`1`。`acc.enabled` 是数字 `0`，而 `0 !== false` 为 `true` —— **这个过滤条件永远放行所有账户**。同一语义在本范围内有 5 种写法，彼此不等价：

| 位置 | 写法 | 对 `0` 的判定 |
|---|---|---|
| `domainSyncJob.ts:322` | `acc.enabled !== false` | 启用（错） |
| `domainSyncJob.ts:54`、`:247` | `Boolean(x.enabled)` | 禁用（若驱动返回字符串 `'0'` 则错） |
| `domainRenewalJob.ts:103` | `!localDomain.enabled` | 禁用（同上） |
| `whois/scheduler.ts:76` | `d.enabled === 0` | 禁用（严格等于数字） |
| `serviceMonitor.ts:797` | `row.enabled === 1 \|\| row.enabled === true` | 禁用（唯一同时兼容布尔与数字） |

**影响**
用户把某个 DNS 账号设为禁用（典型动机：密钥泄露、账单停付、迁移中），`executeDomainSync` 仍会为它建适配器、拉域名列表，并在"提供商列表里没有该域名"时执行 `DomainOperations.update(id, {enabled: 0})`（`:255`）—— **批量禁用该账号下所有域名**并写审计。禁用账号本应完全不产生副作用。
且五种写法任选一种当标准，都会让另外四处行为改变，没有单一归一化点。

**修复方向**
在 BAL 出口提供归一化函数并全量替换：
```ts
export function isEnabled(v: unknown): boolean { return v === 1 || v === true || v === '1'; }
```
更彻底的做法是在 BAL 内把 `enabled` 转成 `boolean` 后再出库，从类型上消灭"数字当布尔"。

### E-07（P1）通知层返回 `void`、动作层恒返回 `{sent:true}`

**位置**：`server/src/service/notification.ts:201`、`:205-208`、`:244-251`；`server/src/workflow/actions/notify/channel.ts:31-32`

**代码摘录**
```ts
export async function sendNotification(title: string, message: string, htmlMessage?: string) {
  if (enabledChannels.length === 0) { log.info('No enabled channels found'); return; }
// channel.ts:31-32
    await sendNotification(title, message);
    return { sent: true };
```

**为什么是隐性问题**
`sendNotification` 没有返回值，调用方无法区分三种语义完全不同的事实：**没有任何渠道被配置**（配置缺失）、**所有渠道都失败**（外部故障）、**全部成功**。它把失败收敛成一条 `warn`（`:244-248`）就返回，属于"把错误变成正常值返回"。同文件的 `sendEmailWithRetry` 是有布尔返回的（`:198` `return result !== null`），说明底层能力具备，只是聚合层丢掉了。

因此 `notify.channel.send` 里的 `return { sent: true }` 是**无条件**的。引擎会把该返回值与 `status:'success'` 一起落进 `workflow_runs.steps`（`engine.ts:258`），运行记录于是显示"通知已发送 = true"而实际零渠道/全失败。

**影响**
- 全站告警路径（NS 监控 `nsMonitorJob.ts:330`、服务监控 `serviceMonitor.ts:760/772`、工作流）都无法知道告警是否真的发出。
- 全新部署未配置任何渠道时，监控面板一切正常、日志只有一条 info，实际零告警能力；工作流运行记录还会把这条链路记成 success，连重试的触发条件都没有。

**修复方向**
```ts
export interface NotifyOutcome { sent: number; failed: number; skipped: 'no-channel' | null }
export async function sendNotification(...): Promise<NotifyOutcome>
```
动作层据此显式失败：`if (outcome.sent === 0) throw new Error(...)`，由引擎记 `status:'failed'` + `error`，用户在运行记录里能直接看到原因。

### E-08（P1）失败切换状态只存进程内存：重启后"自动回切"永久失效

**位置**：`server/src/service/serviceMonitor.ts:488`、`:531`、`:582-591`

**代码摘录**
```ts
const FAILOVER_STATE: Record<number, { usingBackup: boolean; lastSwitchTime: number }> = {};
...
if (primaryAvailable && state.usingBackup && config.autoSwitchBack !== false) {
```

**为什么是隐性问题**
`dns_failover` 是一个两态状态机（primary / backup），但"当前在哪一态"只存在模块级对象里，真正的状态在提供商侧的 DNS 记录上。进程重启后 `FAILOVER_STATE` 清空 → `state.usingBackup = false`：
- 主站仍不可用、DNS 仍指向备用：进入 `!primaryAvailable` 分支重新切到同一个备用（幂等，可接受）；
- **主站恢复、DNS 仍指向备用**：`primaryAvailable && !state.usingBackup` 成立 → 直接返回 `{ status:'ok', resultData:{ activeValue: primaryValue, usingBackup:false } }`（`:533-534`），回切分支（要求 `state.usingBackup`）永远走不到。结果：真实 DNS 仍指向备用，监控状态却显示 `ok` 且 `activeValue` 为主站地址。

**影响**
一次重启就能让 failover "看起来正常、实际卡在备用"。用户在监控面板看到 `ok` 与主站地址，流量却一直打到备用机（容量不足、按量计费）。这是"状态存在两处（内存/提供商）却只维护一处"的典型后果，且没有任何日志提示。

**修复方向**
以持久化/可回读的权威为准：每次检查先 `DnsProviderService.getRecords` 读回记录当前值，与 `config.primaryValue` 比较得出 `usingBackup`（内存只做节流缓存）；或把 `usingBackup` 落到 `servicemonitor_status.result_data` 并在启动时读回。二者取一，且必须与 `resultData.activeValue` 同源。

### E-09（P1）资源采样把"环形缓冲长度"当累计计数，且在采样函数里就地清零

**位置**：`server/src/service/resource/cache.ts:123-138`、`:159`；调用频次见 `resource/job.ts:19-26`、`:28-35`

**代码摘录**
```ts
const deltaHttpProbes = httpCount - lastHttpCount;   // httpCount = httpRing.values.length
lastDbQueries = dbQueries;                           // 在 buildSnapshot 内部就地清零基线
```

**为什么是隐性问题**
两层语义错误叠加：
1. **有界容器当计数器**：`RingBuffer.values.length` 写满后恒等于 `maxSize`（http 5000 / dns 2000 / 各 2000，`:83-86`），此后 `delta` 恒为 0。运行一段时间后 `http_probe_count`/`dns_probe_count` 永久变成 0，而 `avg/p50/p95/p99` 仍正常（基于内容），面板上出现"有延迟数据但请求数为 0"。
2. **采样函数带副作用**：`buildSnapshot` 不纯，它消费并重置 `lastDbQueries/lastErrors/lastReads/lastWrites`；而它每分钟被调用两次——10 秒广播一次（`job.ts:19-26`）、60 秒落库一次（`job.ts:39`）。落库那次拿到的 delta 只覆盖"上一个 10 秒窗口"，写进 `resource_metrics_history` 的 `db_queries_total`/`db_errors_total` 系统性偏小约 6 倍。`clearProbes()`（`:185-190`）在 flush 后还会重置一次探针基线，构成第二个清零点。

**影响**
历史资源曲线长期失真（请求数偏小、探针数最终归零），不报错；任何基于"DB 查询总数下降"的排障判断都会被误导。

**修复方向**
计数器与采样分离：探针用单调递增的模块级 `let httpProbeTotal = 0`（在 `pushHttpProbe` 里 `++`），`buildSnapshot` 只读不写；"读取并清零基线"抽成显式 `consumeDeltas()`，只允许落库路径（60s）调用，10s 广播路径传 `consume: false`。

### E-10（P1）"无法判定可达性"被折叠成"不可达"，真的会切 DNS

**位置**：`server/src/service/serviceMonitor.ts:679-682`、`:671`、`:705`

**代码摘录**
```ts
if (!isSafeMonitorHost(ip)) { log.warn('Invalid monitor target rejected', { target: ip, method }); return false; }
...
child.on('error', () => done(false));       // ping 可执行文件不存在也走这里
```

**为什么是隐性问题**
`checkIpAvailabilitySimple` 的返回类型是 `Promise<boolean>`，把至少四种不同事实压成 `false`：目标非法（配置错误）、ping 二进制缺失（环境问题）、探测自身超时、目标真的不可达。它的返回值在 `checkFailover` 里被直接当作"主站挂了"的判据（`:528` → `:538`），为 `false` 就进入写 DNS 的分支（`:555-575` `updateFailoverDnsRecord`）。

### E-12（P2）失败/重试路径不清超时定时器，残留最长 30 分钟的定时器

**位置**：`server/src/service/taskManager.ts:260-276`

**代码摘录**
```ts
await executionPromise;
if (timeoutId) clearTimeout(timeoutId);
```

**为什么是隐性问题**
`clearTimeout` 只在成功路径执行。任务抛错时（`catch` 分支 `:289-324`）`timeoutId` 从未被清除，而兜底超时是 30 分钟（`DEFAULT_TASK_TIMEOUT_MS`，`:56`），该定时器也**没有 `unref()`**（对比 `:226` 的 defer 定时器有 unref）。每失败一次就留下一个最长 30 分钟的活跃 timer：保持事件循环存活，`server.close()` 之后的优雅退出会被它拖住（root.ai.md §优雅关闭要求按序停止各任务），到点后还会对已 settle 的 Promise 再 reject 一次。

**影响**
提供商 API 抖动导致定时任务频繁失败的环境里，timer 数量随失败次数累积，进程无法按时退出；容器编排下表现为"stop 超时后被 SIGKILL"，丢失优雅关闭阶段的连接清理。

**修复方向**
把清理放进 `finally` 并对定时器 `unref()`：
```ts
try { await executionPromise; } finally { if (timeoutId) { clearTimeout(timeoutId); timeoutId = null; } }
```
`executeTask` 已有外层 `finally`（`:325`），把 `clearTimeout` 上移到那里最省事。
