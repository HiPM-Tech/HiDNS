## 结论

1. `Line` 一个字段在三类提供商里分别是"线路 ID""Cloudflare/ESA 代理开关""被单向改写的 lego 名"，且线路选项 id 空间与记录 `Line` 值空间不一致——5aa3285 只统一了选项 id，没统一记录值，读写两侧至今对不上。
2. 读接口 `Promise<PageResult<T>>` 无法表达失败，适配器把错误统一降级成 `{ total: 0, list: [] }`（实测 92 处），且这个空值会被 `recordCountCache` 当成真实计数写进数据库。
3. 能力位（`DnsCapabilities`）只有前端在消费，服务端零校验；`weight`/`status` 与真实行为漂移；解析器侧还存在"声明走代理实际直连"的静默降级与原生 `fetch`。

### B-01 · P0 · `Line` 一字段三义，且读/写/选项三套词汇表对不上

**位置与原文**

- `server/src/lib/dns/providers/cloudflare/adapter.ts:354`
~~~ts
Line: r.proxied ? '1' : '0',
~~~
  `:433-437` 反向解释：`if (line === '1') return true;` / `if (line === '0') return false;`
- `server/src/lib/dns/providers/aliyunesa/adapter.ts:176`（`:238/247/294/303` 同）
~~~ts
params.Proxied = line === '1' ? 'true' : 'false';
~~~
- `server/src/lib/dns/providers/powerdns/adapter.ts:175` 与 `:393`
~~~ts
Line: 'default',                       // :175  mapRecord
return [{ id: '0', name: '默认' }];    // :393  getRecordLines
~~~
- `server/src/lib/dns/providers/namesilo/adapter.ts:191` 与 `:179`
~~~ts
private mapRecord(r: XmlDict, line = 'default'): DnsRecord {   // :191，:200 处 Line: line
return [{ id: '0', name: '默认' }];                            // :179 getRecordLines
~~~
- `server/src/lib/dns/providers/dnsneko/adapter.ts:376-379`
~~~ts
'0': 'default',
'1': 'default',
~~~
- `server/src/lib/dns/providers/aliyun/adapter.ts:23` 与 `:211`（读侧被改写，选项侧不被改写）
~~~ts
Line: this.normalizeLine(safeString(item.Line)) ?? '0',   // '10=1' → 'unicom'
id: safeString(row.LineCode),                             // 仍是原生 '10=1'
~~~

**为什么是隐性问题**

同一个 `Line` 字段在三种语义间摇摆，而 `DnsRecord` 里没有任何字段能表达"这条记录是被代理而不是被分线路"。Cloudflare 与阿里云 ESA 把 `Line` 当布尔代理位；阿里云/DNSPod/雨云把它当线路 ID；`dnsneko` 还把 `'1'` 在写路径上合并进 `'default'`。同时**读出来的值**（`'default'`、`'unicom'`、`'1'`）不保证是 **`getRecordLines()` 返回的 id 集合**（`'0'`、`'10=1'`）的成员——`powerdns`、`namesilo` 是纯粹的两套值：记录侧 `'default'`，选项侧 `'0'`。

**证据链**：`git show 5aa3285`（提交信息"统一所有DNS提供商默认线路ID为'0'，确保前后端一致性"）里，`west` 同时改了 `getRecordLines` 与 `mapRecord` 的 `Line`，而 `powerdns`/`namesilo` 只改了 `getRecordLines`——同一语义两个调用点各改一处，漏改即成永久不一致。

**影响**

- 前端拿 `record.Line` 去和选项 id 比对（选项来自 `getRecordLines`，见 `client/src/components/RecordForm.tsx:362`），`'default'` 永远匹配不到 `'0'`，线路下拉显示为空/回落到首项。
- 用户只改 TTL 提交时，表单带着选项的 `'0'` 回写；`dnspod/adapter.ts:253-254` 的 `RecordLine: line || '0'` 把原"电信"记录静默改成默认线路，分流规则丢失但接口返回 `true`。
- `Line` 被当代理位时，任何"线路"语义的读取者（报表、同步、工作流 DSL）都会把"已代理"读成"线路 1"。
- 上层只能靠 `providerType === 'cloudflare' / 'aliyunesa'` 硬编码才能读懂（`client/src/components/RecordForm.tsx:340-341`），这正是"接口表达不了真实数据"的直接后果。

**修复方向**

在 `DnsRecord` 上把语义拆开：新增 `Proxied?: boolean`（或统一到已有的 `Cloudflare.proxied`），`Line` 只承载线路 ID；新增单一归一化点 `normalizeLineId(providerType, raw): string` 与 `toProviderLineArg(providerType, id): string`（双向、同一张表），`mapRecord` 与 `getRecordLines` 都必须经过它；对不支持的提供商标记 `lines: 'default-only'` 能力位，禁止用 `'0'` 冒充。迁移期给 `Line` 加 deprecated 注释，并在 CI 里禁止新代码读 `Line === '1'`。

### B-02 · P0 · 读失败 = 空结果（92 处），且空值被写进数据库

**位置与原文**

- `server/src/lib/dns/DnsInterface.ts:37-47`（签名本身没有失败分支）
~~~ts
getDomainList(keyword?: string, page?: number, pageSize?: number): Promise<PageResult<DomainInfo>>;
getDomainRecords(...): Promise<PageResult<DnsRecord>>;
~~~
- `server/src/lib/dns/providers/cloudflare/adapter.ts:194,203,220`
~~~ts
return { total: 0, list: [] };   // zoneId 解析失败 / zone 校验失败 / API success=false
~~~
- `server/src/lib/dns/providers/aliyun/adapter.ts:111-114`（统一 catch）
~~~ts
this.error = e instanceof Error ? e.message : String(e);
return { total: 0, list: [] };
~~~
- 影响面（`server/src/service/recordCountCache.ts:19-23`）
~~~ts
const result = await dnsAdapter.getDomainRecords(1, 10);
if (result.total !== domain.record_count) {
  await DomainOperations.updateRecordCount(domain.id, result.total);
~~~

统计：`server/src/lib/dns/providers/**` 中 `return { total: 0, list: [] }` 共 **92 处**（`grep "total: 0, list: \[\]"`），覆盖 hidns/vps8/jdcloud/huawei/bt/powerdns/tencenteo/dnspod/aliyun/hidns_v2/dnshe/spaceship/dnsla/dnsneko/rainyun/baidu/caihongdns/west/gcore/aliyunesa/cloudflare/qingcloud/huoshan/namesilo 全部实现文件。

**为什么是隐性问题**

`PageResult<T>` 只有 `total`/`list`，没有"这次是失败还是真的没有"的位置，于是每个适配器各自发明"空列表"当错误值。调用方拿到的对象在结构上完全合法，`code === 0` 照常返回，用户看到"该域名暂无记录"。`this.error` 是唯一的旁路信号，但它可变、只在紧邻的 `getError()` 调用里有意义，而且大多数成功路径不清空它（对照 `cloudflare/adapter.ts:162` 只在 `getDomainList` 成功时清空）——于是 `error` 既可能是过期值，也可能在被吞掉后无人读取。

**影响**

- 令牌过期/权限不足/网络故障 → 用户界面显示"空域名列表"，用户会去重复添加账号；记录页显示"无记录"，用户可能重新创建同名记录造成重复。
- 定时任务 `recordCountCache` 把 0 写库（`recordCountCache.ts:21-22`），仪表盘的记录计数被持久化成错误值，且下次刷新前不会自愈。
- `record-lookup.ts:18-23` 把空列表当作"记录不存在"，写成功后的事件不发布（该文件注释已承认此类事故）。

**修复方向**

把失败纳入类型：`type AdapterResult<T> = { ok: true; data: T } | { ok: false; reason: 'auth' | 'network' | 'unsupported' | 'notfound'; message: string; retryable: boolean }`，读方法统一返回它（或抛 `ProviderError`）；过渡期最小改动是给 `PageResult` 加 `degraded?: { reason: string }`，并在 `recordCountCache` 里"有 degraded 就跳过写库"。同时把 `this.error` 换成返回值，禁止旁路字符串。

### B-03 · P0 · RecordId 契约破裂：字面量当 ID，非法 ID 变 0 号记录

**位置与原文**

- `server/src/lib/dns/providers/bt/adapter.ts:205-206`
~~~ts
await this.request('/api/v1/dns/record/create', params);
return 'success';
~~~
- `server/src/lib/dns/providers/powerdns/adapter.ts:244`
~~~ts
return 'success';
~~~
- `server/src/lib/dns/providers/dnspod/adapter.ts:277`（`:184/224/249/262/290` 同型）
~~~ts
RecordId: toNumber(recordId, 0),
~~~
- `server/src/lib/dns/providers/common.ts:23-26`（把任意非法值静默变 0 的源头）
~~~ts
export function toNumber(value: unknown, fallback = 0): number {
~~~

同类：`dnshe/adapter.ts:341,365`、`rainyun/adapter.ts:301,337` 的 `record_id: toNumber(recordId, 0)`。

**为什么是隐性问题**

`addDomainRecord(): Promise<string | null>` 的返回值语义是"提供商侧记录 ID"，调用方会把它存进 `third_id` 列，后续 update/delete/status 全靠它。返回 `'success'` 让这一列永久存着一个不存在的 ID：本次请求看起来成功（非 null，路由判成功），下一次对同一条记录的更新必然失败，且失败信息与"记录被外部删除"无法区分。反向方向同样危险：`toNumber(recordId, 0)` 把 `''`、`'abc'`、`'undefined'`、`null` 一律变成 `0`，于是"ID 非法"被翻译成"操作 0 号记录"——在 DNSPod 这类自增 ID 的提供商上，0 号不一定不存在。

**影响**

- BT/PowerDNS 用户新建记录后：`third_id='success'`，编辑/删除/启停全部失败，且前端拿到的是"操作失败"级别的模糊错误；同步任务把该记录判为"提供商侧已消失"，可能反复重建。
- 任何人用一个畸形 `recordId`（路由参数直传）调用删除：`toNumber('abc',0)=0` → 向提供商发 `RecordId=0` 的删除请求。命中即误删，不命中就是一条误导性的错误日志。

**修复方向**

`addDomainRecord` 在拿不到真实 ID 时必须返回 `null` 并置 `error='provider did not return record id'`（禁止编造）；所有 `toNumber(recordId, 0)` 改为 `parseRecordId(recordId): string`（非空、匹配 `^[A-Za-z0-9_-]+$` 才返回，否则抛 `INVALID_RECORD_ID`），并在 `DnsHelper.createLoggingAdapter` 出口统一校验 ID 形态。加一条 CI 断言：适配器源码中禁止出现 `return 'success'`。

~~~ts
  return [
    { id: '0', name: '默认' },
~~~

- `server/src/lib/dns/providers/aliyun/adapter.ts:215-216`
~~~ts

  return [{ id: '0', name: '默认' }];
~~~
- `server/src/lib/dns/providers/dnsneko/adapter.ts:342,359-361`（三处同型）

**为什么是隐性问题**

`getRecordLines(): Promise<Array<{id,name}>>` 同样没有失败通道。于是失败时有两种退化：DNSPod/阿里云/DnsNeko **收窄**成单条默认线（用户以为这个账号只有默认线路），BT **编造** 5 条（`'0'..'4'` + 中文名），后者把不存在的 `viewId` 当成合法输入交给写路径（`bt/adapter.ts:238 view_id: toNumber(line, 0)`）。这是"用假数据把错误包装成正常空态"的典型。

**影响**

- 失败一次（token 到期/接口抖动）后打开记录编辑：线路下拉只剩"默认"。用户为了改 TTL 保存，记录被搬到默认线路；原来按电信/联通分流的解析结果立刻改变，且由于 B-01 的写路径 `line || '0'`，服务端返回 `true`。
- BT 用户选到"电信"（编造的 id `'1'`）：请求打到不存在的 view，要么报错，要么被提供商忽略后写到默认线路——两种结果都不告诉用户"线路没生效"。

**修复方向**

`getRecordLines` 改为返回 `{ lines: LineOption[]; degraded: boolean; reason?: string }`（或抛错）；前端在 `degraded` 时禁用线路选择并提示"无法获取线路，保存将保留当前线路"；服务端在 `line` 缺省时**不发送**该字段（而不是补 `'0'`），让提供商保持原值。禁止任何适配器在 catch 里构造未从 API 取得的选项。

### B-05 · P1 · 能力位与服务端行为漂移，布尔返回混淆"不支持"与"失败"

**位置与原文**

- `server/src/lib/dns/providers/registry.ts:135`（Cloudflare 声明 weight=true）
~~~ts
capabilities: { dns: { remark: true, status: false, redirect: true, weight: true, proxiable: true, cnameFlattening: true, recordTypes: CLOUDFLARE_RECORD_TYPES }, log: false, renewal: false },
~~~

- `server/src/lib/dns/providers/cloudflare/adapter.ts:395`（写路径丢弃 weight）
~~~ts
// Cloudflare DNS records do not support a generic "weight" field for most types.
~~~
- `server/src/lib/dns/DnsInterface.ts:71`
~~~ts
setDomainRecordStatus(recordId: string, status: number): Promise<boolean>;
~~~
- `server/src/lib/dns/providers/namesilo/adapter.ts:173-176`
~~~ts
async setDomainRecordStatus(_recordId: string, _status: number): Promise<boolean> {
  this.error = 'NameSilo does not support record status toggle';
~~~

**为什么是隐性问题**

- `weight` 是"按记录类型生效"的能力（Cloudflare 只有 SRV/URI 有 `data.weight`），但 `DnsCapabilities.weight` 是布尔、与会话级能力位同级，无法表达"仅 SRV"。于是 UI 对 A 记录也显示权重输入框，服务端静默丢弃（`cloudflare/adapter.ts:377-397` 里 `weight` 只在 SRV 分支用掉）。

**影响**

- 通过 API Token 调记录创建接口传 `weight: 20`：DNSPod 生效、Cloudflare 丢弃、`weight:false` 的提供商全部丢弃，三方响应完全一样。DDNS/acme 类外部集成无法判断"我的 weight 到底写进去了没有"。
- 前端隐藏启停按钮的提供商，用户改用 API 调 `setDomainRecordStatus`，得到 `false` + 500，日志里只有 "NameSilo does not support..."，告警系统会当成真实故障。

**修复方向**

`DnsCapabilities.weight` 改为 `weight: false | 'srv-only' | true`（或 `weightRecordTypes: RecordType[]`），`status` 保留布尔但服务端**必须**在写路径校验：能力位为假时直接返回 `409 CAPABILITY_UNSUPPORTED`（显式豁免路径除外）。`setDomainRecordStatus` 返回类型改为 `Promise<void>` 并抛 `UnsupportedCapabilityError`；布尔返回值只保留给临时失败。补一条契约测试：每个 `capabilities.dns.X === false` 的提供商，其对应写方法必须抛 `UnsupportedCapabilityError`。

### B-10 · P1 · 注释写 `Promise.race`，实现是 `Promise.all`；priority 不影响延迟

**位置与原文**

- `server/src/lib/dns/resolver/resolver.ts:132-134`
~~~ts
// 使用 Promise.race 获取最快结果
const results = await Promise.all(queries);
const successResult = results.find(r => r?.success);
~~~
- `server/src/lib/dns/resolver/resolver.ts:332-333`（明文分支同型）

**为什么是隐性问题**

**修复方向**

   **不要**把它"统一"成和其它 92 处一样返回 `{total:0,list:[]}`。这是本仓库读路径唯一的正确样板，B-02 的修法应以它为模板向内收敛，而不是把它拉平。

2. `server/src/lib/dns/providers/registry.ts:352-391` —— `validateDefinitions` / `validateCredentialSharing` 在模块加载期**直接抛错**（重复 type、重复 config key、凭据复用声明不一致、引用不存在的提供商）。
   **不要**为了"启动更宽容"改成 `warn` 或 `try/catch` 后继续。这符合"默认拒绝 + 显式豁免"，把半截授权带起来才是真风险（`registry.ts:373-377` 注释已说明动机）。

3. `server/src/lib/dns/DnsHelper.ts:20-32` —— `getProviders` 采用惰性求值，注释说明了 `registry → providers/index → extra → dns-provider-service → DnsHelper → registry` 的环与 TDZ 风险。
   **不要**改回模块顶层的 `const PROVIDERS = getProviderInfoList()`。那会在"从 registry 侧进入"时撞上 `providerDefinitions` 的 TDZ，表现为个别入口随机 `Cannot access before initialization`。

4. `server/src/lib/dns/providers/http.ts:32-55` —— `performRequest` 用 `AbortController` + `finally clearTimeout` 统一超时，并经 `fetchWithFallback(url, init, useProxy, providerName)` 发请求。
   **不要**为了"少一层封装"让 provider 自己发请求。B-06 的违规点在 resolver（`doh-resolver.ts:261`），不构成放宽 provider 侧约束的理由；也**不要**把 `http.ts` 的 `timeoutMs` 默认值改成无超时。

5. `server/src/lib/dns/providers/availability.ts:18-21` + `registry.ts:402-404` —— 虚拟提供商"生产硬关闭 + 必须显式开启 + 未开启就根本不注册"。
   **不要**改成"总是注册、运行时再判断"，也不要去掉 `NODE_ENV` 检查。它让"忘设环境变量"的结果是关闭而不是打开，属于正确的失败关闭。

6. `server/src/lib/dns/providers/common.ts:23-31` —— `toNumber` / `toRecordStatus` 本身**不是**缺陷：`toRecordStatus` 对 `'DISABLE'/'DISABLED'` 返回 0、其余返回 1，符合"未知即启用"的既有契约（DNSPod/阿里云只返回 ENABLE/DISABLE）。
   **不要**把 `toNumber` 全局改成"非法即抛"。B-03 的问题在**调用点**把 fallback 传成 `0` 当记录 ID 用；改函数会波及约 145 处正常用法（如 `TTL: toNumber(row.ttl, 600)`）。

7. `server/src/lib/dns/resolver/resolver.ts:33-70` —— "加密 → 明文 → 系统 DNS"三级回退链是 `root.ai.md:459-465` 明确要求的设计。
   **不要**因为 B-07（空答案当失败）就删掉回退链或改成"只用 DoH"。正确改法是给 `DNSResponse` 补 `rcode` 并让 NXDOMAIN 短路（nxdomain 不触发回退），而不是取消降级。
