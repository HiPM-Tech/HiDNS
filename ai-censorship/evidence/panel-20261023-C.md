## 结论

1. 「默认拒绝 + 显式豁免」只做到了一半：门禁本身用**大小写敏感**的字符串前缀判断，而 Express 路由默认大小写不敏感，`/API/...` 直接绕过 503；同时初始化入口守卫把三态压成布尔，项目里唯一实现 fail-closed 的 `isInitSurfaceOpen()` **从未被调用**，数据库不可达时 `/api/init/database` 仍然开放（P0）。
2. 响应契约存在三套写法（`sendError` 默认 HTTP 200 / `errorHandler` 用 `message`+`timestamp` / `security.ts` 用 `code:1`），文档只承认 `{code,data,msg}`；120 处错误路径（含权限拒绝）以 HTTP 200 返回。
3. 权限判定与限流各有多份实现且互相矛盾：Token 空域名数组 = 全放行（两处独立实现）、登录限流与其余限流用了两套可被伪造的客户端 IP、`/api/security` 挂了两个路由器导致 5 个端点静默不可达。

## 逐条详情

### C-01（P0）初始化入口守卫把三态压成布尔，`isInitSurfaceOpen()` 是死代码

- 位置：`server/src/routes/init.ts:49-58`、`server/src/service/systemState.ts:71-73`、`server/src/app.ts:205-210`
- 代码摘录：
  ```ts
  // init.ts:51-58
  await refreshSystemState();
  if (isSystemInitialized()) { ... res.status(403)... return; }
  ```
  ```ts
  // systemState.ts:71-73
  export function isInitSurfaceOpen(): boolean {
    return !initialized && lastProbe === 'uninitialized';
  }
  ```
- 为什么是隐性问题：`systemState.ts` 自己写明「初始状态默认为不可达，即 fail-closed：首次探测完成前初始化入口保持关闭」，并且为此专门导出了 `isInitSurfaceOpen()`。但全仓检索显示该函数**只在 `systemState.test.ts` 里被调用**，`app.ts:207` 把它 import 进来后没有任何使用点（未使用导入），`init.ts` 的 `requireInitSurface` 只判断 `isSystemInitialized()`。于是 `lastProbe === 'unreachable'` 与 `'uninitialized'` 在守卫处被压成同一个分支——三态设计在唯一的执行点上退化成了布尔。测试全绿（单测直接测 `isInitSurfaceOpen` 本身），所以静态检查与 CI 都不会报警。
- 影响：全新部署（无 `data/.initialized` 标记）且数据库当时不可达时：`requireInitSurface` 探测得到 `unreachable` → `initialized` 仍为 false → 放行 → `POST /api/init/database`（init.ts:184）走 Scenario C，用**请求体里的**数据库配置 `saveDatabaseConfig` + `applyDatabaseConfig` 重建连接并 `initializeSchema()`，随后 `POST /api/init/admin`（init.ts:308，此时 state 已是 `uninitialized`，schema 已由攻击者建好）创建管理员并 `markInitialized()`。结果是把「一次数据库抖动」转换成 `root.ai.md` §数据库可用性判定里点名的"未授权接管通道"：实例被指向攻击者的库，原库被丢弃。同一守卫下 `/admin` 却单独判了 `unreachable` 并返回 503（init.ts:313），两个状态变更端点守卫强度不一致，进一步说明这是漏接而不是有意设计。
- 修复方向：`requireInitSurface` 改为以 `isInitSurfaceOpen()` 为唯一判据，非开放时统一 403（`unreachable` 用 503 更贴切但必须拒绝）；`app.ts` 的 `initCheckMiddleware` 同样改用该函数，并删掉未使用的 import。给 `/database`、`/admin`、`/test-db` 补一条「`getLastProbe() !== 'uninitialized'` 即拒绝」的集成测试（现有测试只覆盖纯函数，覆盖不到这条链）。
- 级别：P0
- 归属：后续引入（`git log` 显示 `systemState.ts`/`init.ts` 的最近改动为 2026-10-13 `fix(db): 初始化标记落盘…`，即加固补丁本身引入了这个未接线点）
- 置信度：HIGH（`isInitSurfaceOpen` 全仓零调用为 grep 实证；放行链路逐行读过）

### C-02（P1）初始化门禁用大小写敏感前缀判断，Express 路由大小写不敏感

- 位置：`server/src/app.ts:470-487`
- 代码摘录：
  ```ts
  if (!req.path.startsWith('/api/')) { return next(); }
  if (isSystemInitialized()) { return next(); }
  ```
- 为什么是隐性问题：`app.ts` 只设置了 `trust proxy`，没有设置 `case sensitive routing`，Express 4 默认是**大小写不敏感**匹配路由；而门禁的判断对象是原始大小写的 `req.path`。两套大小写语义不一致，导致门禁只覆盖"规范写法"的 URL，路由却接受任意大小写。这不是"少配了一个中间件"，而是判据和实际匹配器不是同一个东西。
- 影响：未初始化/降级模式下 `GET /API/mcp/status` 命中 `req.path = '/API/mcp/status'` → 不以 `/api/` 开头 → `next()` 放行 → `app.use('/api/mcp', …)` 大小写不敏感命中 → `mcp-config.ts:98` 的 `/status` 是**未鉴权**处理器，它会去查 `McpOperations.getGlobalConfig()`，在 `:memory:` 临时库（app.ts:7-10）或降级库里直接 500 并把 `error.message` 原文回给匿名调用者（mcp-config.ts:104），泄露表结构/驱动错误。同样地，携带旧 JWT cookie 的请求可以绕过 503 访问全部业务路由。文档承诺的"除豁免外一律 503"（`root.ai.md` §路由 1）实际不成立。
- 修复方向：判据统一成 `req.path.toLowerCase()`（或改用 `req.baseUrl + req.path` 归一化后的值），并在 `app.set('case sensitive routing', true)` 与归一化之间只选一条路走；同时把 `/status` 这类会碰数据库的未鉴权端点改成不返回原始错误消息。
- 级别：P1
- 归属：后续引入（该门禁为"默认拒绝 + 显式豁免"重写版，注释自称历史实现遗漏 10 个前缀）
- 置信度：HIGH（`req.path` 语义与 Express 默认 `case sensitive routing=false` 均可核实；`mcp-config.ts:98` 无 authMiddleware 为原文）

### C-03（P1）`sendError` 默认 `statusCode = 200`，120 处错误路径返回 HTTP 200

- 位置：`server/src/utils/http.ts:77-83`
- 代码摘录：
  ```ts
  export function sendError(res: Response, msg: string, statusCode = 200, data?: unknown): Response {
    return res.status(statusCode).json({ code: statusCode >= 400 ? statusCode : -1, data, msg });
  ```
- 为什么是隐性问题：同一个函数里，`statusCode` 同时承担「HTTP 状态码」和「业务错误码」两种语义；缺省值取 200 时二者分离——HTTP 说成功、`code` 说失败。调用点看不出差别（`sendError(res, 'Permission denied')` 读起来完全正常），只有翻实现才知道它返回 200。全仓统计：242 处 `sendError` 中 **120 处省略了 statusCode**，包括 `records.ts:438`、`records.ts:687`、`users.ts:196`、`domains.ts:502`、`accounts.ts:188`、`providers.ts:103` 这些权限拒绝。
- 影响：任何以 HTTP 状态为准的消费者都会把拒绝当成功——`docs/api.md` §外部应用集成列出的 DDNS-Go / acme.sh 适配器、反代/WAF 的 4xx 规则、`requestLogger.ts:21` 的告警分级（这些响应只记 debug）、以及 `errorHandler` 之外的所有监控。前端靠 `code !== 0` 兜住了，所以页面看起来是对的，缺陷只在机器消费侧暴露。
- 修复方向：把缺省值改成必填，或在函数内部按 msg 无法推断时**必须显式传**：`export function sendError(res, msg, statusCode: number, data?)`，让 120 个调用点在编译期暴露；短期内至少把权限/未找到/校验三类改成 `403/404/400`。
- 级别：P1
- 归属：0.0.1 存量（`utils/http.ts` 最近提交 2026-04-08 三层数据库重构，早于当前 API 文档口径）
- 置信度：HIGH（默认值与 120 处调用点均为 grep + read 实证）

### C-04（P1）Token 域名白名单空数组 = 全放行，同一函数内注释自相矛盾

- 位置：`server/src/middleware/auth.ts:159-175`、`server/src/service/token.ts:181-186`
- 代码摘录：
  ```ts
  // auth.ts:160  「如果为空数组 []，表示不允许任何域名（白名单机制）」
  // auth.ts:166  「空数组表示允许所有域名（向后兼容 ddns-go 等外部工具）」
  if (tokenPayload.allowedDomains.length === 0) { ... next(); return; }
  ```
- 为什么是隐性问题：同一段注释里对 `[]` 给出两个互斥语义，说明这里没有定论；实现选了"全放行"。同时"未限制"用了三个哨兵：`null`、`undefined`、`[]` 全部等于全放行，因此**没有任何取值能表达"不允许任何域名"**——白名单机制缺了空集这一态。同一语义还有第二份实现（`token.ts:184` 的 `allowedDomains.length === 0`），两处都改才生效。
- 影响：创建令牌时 `tokens.ts:134` 只校验 `!allowed_domains`（`[]` 为真值，能过），`tokens.ts:146` 又把 `allowed_services` 硬编码成 `['*']`。于是"域名一个都没勾"这个最自然的初始表单态，产出的是一个**对全部域名、全部服务有效**的令牌；用户以为自己收窄了权限，实际给了最大权限。两处实现任一被单独修改，另一处仍会放行。
- 修复方向：确立单一判据 `isDomainAllowed(payload, domainId)`：`null/undefined` → 全放行（仅兼容期）、`[]` → 拒绝、非空 → `includes`；`auth.ts` 与 `token.ts` 都改为调用它，并删掉矛盾注释。同时让 `tokens.ts` 对 `allowed_services` 使用请求体而非 `['*']`。
- 级别：P1
- 归属：0.0.1 存量（注释明确写着"向后兼容 ddns-go"）
- 置信度：HIGH

### C-05（P1）`rdapLimiter` 只检查 Authorization 头"存在"就跳过限流

- 位置：`server/src/middleware/rateLimit.ts:94-99`
- 代码摘录：
  ```ts
  const hasBearerToken = req.headers.authorization?.startsWith('Bearer ');
  return hasSessionCookie || !!hasBearerToken;
  ```
- 为什么是隐性问题：`skip` 判定的是"请求头形态"，而不是"认证是否通过"。限流器挂在 `app.use('/api/rdap', rdapLimiter, rdapRouter)`（app.ts:506），该挂载点**在** `authMiddleware` 之前，本来也拿不到认证结果——所以这里不可能判真伪，注释里的"已认证"是拿不到的事实。同理 `req.cookies.token` 也是客户端可自行设置的字段。
- 影响：`/api/rdap` 是初始化豁免的公开路由，`rdap.ts:211` 会对每个请求发起真实的 WHOIS/RDAP 上游查询（`useCache:false`，明确不使用缓存）。攻击者带上任意 `Authorization: Bearer x` 即可把 2 req/s 的上限去掉，把 HiDNS 变成不限速的公开 WHOIS 代理，并顺带刷爆上游速率与本地日志（每个请求 `rdap.ts:49,238,257/268` 至少 3-4 条 info）。
- 修复方向：改为"只有真正通过认证才跳过"——把限流器挂到需要认证的分支之后，或在 `skip` 里做一次廉价校验（`verifyToken` 的缓存命中判定）；否则直接删掉 skip，公开接口一律 2 req/s。
- 级别：P1
- 归属：0.0.1 存量（`git log`：2026-06-09 `feat(server): add rate limit for RDAP public queries`）
- 置信度：HIGH

### C-06（P1）客户端 IP 两套口径，登录限流走可伪造的 XFF

- 位置：`server/src/middleware/clientIP.ts:52-63`、`server/src/middleware/rateLimit.ts:15-20`、`server/src/routes/auth.ts:537,561`
- 代码摘录：
  ```ts
  // clientIP.ts:52-62  只要 socket 对端是内网，就直接采信 XFF 第一个值
  if (remoteAddr && isPrivateIP(remoteAddr)) { ... return ips[0]; }
  ```
  ```ts
  // rateLimit.ts:18
  const ip = getRequestIP(req) || 'unknown';
  ```
- 为什么是隐性问题：同一份"客户端 IP"在两个地方算法不同：`loginLimiter`/`emailLimiter` 用 `getRequestIP()`（自行采信 XFF），`initLimiter`/`rdapLimiter`/`apiLimiter` 用 express-rate-limit 默认的 `req.ip`（走 `trust proxy`）。两套口径在开发/默认部署下结论相反：`trust proxy` 只在 `NODE_ENV=production` 或显式 `TRUST_PROXY` 时才设置（app.ts:321-332），而 `getClientIP` 无条件对内网对端采信 XFF。注释还写着"不修改 req.ip，因为它是 Express 的只读属性"，等于承认两条路不会收敛。
- 影响：HiDNS 直连公网但前面有同机 Nginx（`root.ai.md` 明示支持的部署）时，任何人直连 3001 端口发 `X-Forwarded-For: 1.2.3.4` 即可：① 每次换一个 XFF 就换一个 `loginLimiter` key 和 `recordFailedAttempt` 的 IP，账号锁定（`root.ai.md` §安全规范"登录限制（IP/设备信任）"）形同虚设；② 反过来伪造受害者 IP 可把锁定打到别人头上；③ `auth.ts:537` 写入的 `ipAddress` 也是审计与登录统计的取值来源，日志里的 IP 不可信。而在同一部署下 `req.ip` 恒为 `127.0.0.1`，`initLimiter` 变成全站共享一个桶。
- 修复方向：只保留一个 IP 来源。推荐删掉 `getClientIP` 里的 XFF 分支，全部改用 `req.ip` + 正确配置 `trust proxy`（把 `TRUST_PROXY` 的默认值从"仅 production"改成显式的部署配置项），`getRequestIP` 退化为 `req.ip` 的别名。
- 级别：P1
- 归属：0.0.1 存量（`clientIP.ts` 最近改动 2026-05-03 `fix(中间件): 修正IP获取逻辑并移除对req.ip的修改`）
- 置信度：HIGH

### C-07（P1）`/api/security` 挂两个路由器，`securityPolicy.ts` 的 5 个端点被静默遮蔽

- 位置：`server/src/app.ts:509-510`、`server/src/routes/security.ts:13,24,36,260,272`、`server/src/routes/securityPolicy.ts:38,80,105,164,187`
- 代码摘录：
  ```ts
  app.use('/api/security', securityRouter);
  app.use('/api/security', securityPolicyRouter);
  ```
- 为什么是隐性问题：两个路由器挂在同一路径，Express 先匹配 `securityRouter`，命中即终止。`securityPolicy.ts` 里的 `GET /policy`、`PUT /policy`、`POST /password-strength`、`GET /trusted-devices`、`DELETE /trusted-devices/:id` 与 `security.ts` 完全同路径同方法，因此**永远不会执行**。它们不是死代码意义上的"没人调用"，而是"注册了、有 swagger 注释、看起来是权威实现、实际不生效"——任何在 `securityPolicy.ts` 里修安全策略 bug 的改动都会显示为已修复但不生效。
- 影响：两份实现的返回契约已经漂移：`PUT /api/security/policy` 在 `security.ts:28` 返回 `{code:0, msg:'Security policy updated'}`（**无 data**），而 `securityPolicy.ts:82` 返回更新后的策略本体并带 swagger 文档；前端若按文档读 `data`，拿到的是 `undefined`，界面显示旧值却不报错。另外 `securityPolicy.ts` 的 5 个端点用 `asyncHandler`（错误进全局处理器），`security.ts` 的用 try/catch + `code:1`（27 处），两套错误口径并存。
- 修复方向：合并成一个路由器（保留 `asyncHandler` + `sendSuccess`/`sendError` 版本），删掉另一份；在 app.ts 里加一行注释说明"同一挂载点只允许一个路由器"。若短期不能合并，至少把重复的 5 个端点从 `securityPolicy.ts` 删除，避免下次改错文件。
- 级别：P1
- 归属：0.0.1 存量（两个文件都在，`securityPolicy.ts` 自 2026-06-07 起未再改动）
- 置信度：HIGH

### C-10（P2）全局错误响应是 `{code,message,timestamp}`，与文档契约 `{code,data,msg}` 不一致

- 位置：`server/src/middleware/errorHandler.ts:50-56,90-95`
- 代码摘录：
  ```ts
  res.status(err.code).json({ code: err.code, message: err.message, details: err.details, timestamp: ... });
  ```
- 为什么是隐性问题：`docs/api.md:17-28` 与 `root.ai.md` §通用响应格式都只承认 `{code,data,msg}`，而 `ApiError` 用的是 `message`/`details`/`timestamp`（没有 `msg`、没有 `data`）。这不是"风格差异"：同一次请求里，业务错误走 `sendError` 给出 `msg`，基础设施错误（body 解析失败、`AppError`、未捕获异常）走 `errorHandler` 给出 `message`，客户端必须写两套解析才能显示错误文案。`security.ts` 又是第三套（`code:1`，27 处），`tunnels.ts`/`webauthn.ts` 是第四套（`code:-1`）。
- 影响：前端 toast 在全局错误路径上取 `msg` 得到 `undefined`，用户看到空提示或英文兜底；外部集成方按文档解析失败。另外该处理器**不检查 `res.headersSent`**：`/api/mcp` 的 SSE/Streamable HTTP（`mcp-protocol.ts`）在流已开始后抛错时，这里会再次 `res.status().json()`，触发 `ERR_HTTP_HEADERS_SENT` 二次异常，掩盖原始错误。
- 修复方向：`ApiError` 统一为 `{code, data: details, msg: message}`（保留 `timestamp` 作为额外字段不冲突）；入口处加 `if (res.headersSent) return next(err);`。
- 级别：P2
- 归属：0.0.1 存量
- 置信度：HIGH

### C-11（P2）`line` 同时当线路 ID 与 CF/ESA 代理开关，同一归一化逻辑写了两遍

- 位置：`server/src/routes/records.ts:470-474`（创建）、`records.ts:719-723`（更新）
- 代码摘录：
  ```ts
  const effectiveLine = cloudflare?.proxied !== undefined
    ? (cloudflare.proxied ? '1' : '0')
    : aliyunesa?.proxied !== undefined ? (aliyunesa.proxied ? '1' : '0')
    : (line ?? '0');
  ```
- 为什么是隐性问题：`line` 一个字段承担两种语义——对 CF/ESA 是"是否走代理"的布尔（`'1'`/`'0'`），对其他 provider 是线路 ID（可以是 `'5'`、`'default'`）。两种语义在同一个三元表达式里按"哪个字段先出现"决胜负，接口签名（`line?: string` + `cloudflare?: {proxied?: boolean}`）无法表达二者互斥。`line ?? '0'` 还把所有 provider 的"未指定线路"钉死成哨兵 `'0'`，而适配器侧另有自己的兜底（本报告不展开，属他人范围），路由这一层已经是一个独立注入点。同一段逻辑在创建与更新各写一份，改一处不会同步另一处。
- 影响：客户端同时提交真实线路（如从 `getRecordLines()` 拿到的 `line:'5'`）与 `cloudflare:{proxied:true}` 时，线路被静默丢弃并写成 `'1'`——用户看到"线路保存成功"，实际记录挂到了默认线路且开了代理。任何针对"线路丢失"的修复如果只改 470-474，更新路径（719-723）仍然错。
- 修复方向：抽一个 `resolveRecordLine({ providerType, line, proxied })`（放在 service 层）作为唯一归一化点，返回值区分 `{ kind: 'proxy', on: boolean } | { kind: 'line', id: string } | { kind: 'default' }`；路由只做校验与转发，禁止在路由里再出现 `'1'`/`'0'` 字面量。
- 级别：P2
- 归属：0.0.1 存量
- 置信度：HIGH

### C-12（P2）`res.json` 与 `res.send` 都被打补丁，每个 JSON 响应记两遍日志

- 位置：`server/src/middleware/requestLogger.ts:46-55`
- 代码摘录：
  ```ts
  res.send = function (data) { doLog(); return originalSend.call(this, data); };
  res.json = function (data) { doLog(); return originalJson.call(this, data); };
  ```
- 为什么是隐性问题：Express 4 的 `res.json` 实现末尾是 `return this.send(body)`（已核对 `node_modules/express/lib/response.js`），而 `this.send` 已被替换成打了 `doLog()` 的版本，因此每个 JSON 响应执行 `doLog()` 两次。代码本身完全看不出这个问题——两个补丁各自都"对"，错在它们的组合。`res.sendFile`/`res.end` 不经过 `send` 的路径又只记一次，所以日志条数取决于响应类型，无法用"每个请求一行"来推断。
- 影响：`root.ai.md` §日志限流 把日志量当强制约束。这里 4xx/5xx 的 warn/error 行数翻倍（`requestLogger.ts:27-38`），故障期间的日志体积与噪声同步翻倍；按状态码做的统计（成功率、错误率）也会整体偏高，反而掩盖真实故障。
- 修复方向：只保留一个挂载点——建议只覆写 `res.end`（或只在 `res.json` 里打 `this._logged = true` 标记，`doLog` 内 `if (this._logged) return;` 幂等）。
- 级别：P2
- 归属：0.0.1 存量
- 置信度：HIGH（Express 源码已核实）
