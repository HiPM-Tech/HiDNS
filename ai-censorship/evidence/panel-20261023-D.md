## 结论

1. 前端最严重的隐性问题不在 UI 层，而在「哨兵值 + 归一化点缺失」：账号配置的 `***` 掩码被当作真值回传，`line` / `enabled` / 默认线路各自有 2–3 套表示，且每个调用点各写一遍判定。
2. `root.ai.md` 的两条 P0+ 硬约束在前端被实质绕过：禁止直接 fetch（Security.tsx 7 处 + 2 处硬编码 `/api`）、表单必须 useFormSync（3 个表单仍是手写 useEffect）。
3. 另有一处影响面很大的隐性缺陷：`useRealtimeData` 依赖不稳定数组字面量，导致每次渲染都拆建 WebSocket 连接。

## 逐条详情

### D-01｜P0｜服务端掩码 `***` 被当作真值回传

- **位置**：`client/src/pages/Accounts.tsx:53`、`:99`、`:124`；对照 `server/src/routes/accounts.ts:137`、`:409`
- **代码摘录**：

```ts
// Accounts.tsx:53（normalizeAccountConfig）
.map(([key, value]) => [key, String(value || '')]),
// Accounts.tsx:99（submitAccount）
onSubmit({ type, name, config: { ...config, useProxy }, remark });
```

- **为什么是隐性问题**：服务端读账号时，在 `showDnsProviderSecrets` 关闭的情况下把**所有** config 键（不只密码）替换成字面量 `'***'`（`accounts.ts:137`）。前端 `normalizeAccountConfig` 不做哨兵识别（只剔除 `useProxy`），`submitAccount` 又把整份 config 原样 PUT 回去；服务端 PUT 同样不识别该哨兵，直接 `updates.config = JSON.stringify(config)`（`accounts.ts:409`）。「掩码」这个只在展示层成立的隐式契约，被写路径当成真值消费了。
- **影响**：管理员在默认配置下编辑一次账号（哪怕只改备注），提交的凭据全是 `***`，`dnsAdapter.check()` 失败并返回 "Credential check failed"，无法保存；若某 provider 的 `check()` 只做形式校验，`***` 会被真正落库，账号凭据永久损坏直到人工重填。团队成员编辑他人账号同样触发。
- **修复方向**：在 api 层建立唯一的哨兵归一化点——`accountsApi.update` 接收 config 时剔除值为 `'***'` 的键（或改成「只提交 dirty 字段」），并在 `api/types.ts` 把账号 config 标注为 masked 语义；`normalizeAccountConfig` 同时返回「未变更字段」集合供提交层过滤。
- **级别**：P0｜**归属**：0.0.1 存量｜**置信度**：HIGH（两端原文均已核实；「*** 落库」分支依赖具体 provider 的 check() 实现，标为 [INFERENCE]）

### D-02｜P1｜`line` 一字段双语义，代理门禁恒真

- **位置**：`client/src/components/RecordForm.tsx:143`、`:159`、`:233-241`、`:330`、`:340-341`；`client/src/pages/Records.tsx:237-239`
- **代码摘录**：

```ts
const hasMultiLine = lines.length > 1 && !proxiable;   // 143
const lineValue = canSelectProxy ? line : undefined;   // 330
```

- **为什么是隐性问题**：`line` 在一个 state 里承担两种语义——对 proxiable 的 provider 它是代理开关（`'0'`/`'1'`，见 `:355-359` 的选项），对多线路 provider 它是线路 ID（`:362`）。`DnsRecord.line?: string`（`api/types.ts:100`）表达不了这个区别。且 `:233-241` 的 `canSelectProxy` 三元表达式两个分支都返回 `true`（`:240` 与 `:241`），所谓「代理可选」门禁从未生效，`:330` 的 `undefined` 分支是死代码；`:182-186` 的补丁 effect 也只在 `prev === '0'` 时才更新线路。
- **影响**：① 任何「既 proxiable 又多线路」的 provider，`hasMultiLine` 被 `!proxiable` 强制为 false，真实线路被静默丢弃，编辑后记录被挪到 `'0'`；② `Records.tsx:237-239` 用 `r.line === '1'` 判定「已代理」，若某 provider 的线路 ID 恰好是 `'1'`，表格会把「线路1」显示成「已代理」；③ `cloudflare.proxied` 由 UI 字符串反推（`:340`），语义链是「UI 字符串 → 布尔」，中间无校验点。
- **修复方向**：把线路与代理拆成两个独立字段（`{ lineId: string; proxied: boolean | null }`），代理能力由 `capabilities.dns.proxiable` 驱动、线路能力由 `lines.length` 驱动，二者正交；`canSelectProxy` 删除或改成 `proxiable || hasMultiLine`。
- **级别**：P1｜**归属**：0.0.1 存量｜**置信度**：HIGH

### D-03｜P1｜默认线路哨兵三写、首项即默认

- **位置**：`client/src/components/RecordForm.tsx:146`、`:364`；`client/src/pages/domains/ServiceMonitorTab.tsx:576`；`client/src/pages/Records.tsx:245`；`client/src/pages/domains/DomainListTab.tsx:68`；`client/src/pages/Accounts.tsx:67,72`
- **代码摘录**：

```ts
if (proxiable) return '0';                                             // RecordForm.tsx:146
: [{ label: t('records.defaultLine') || '默认', value: 'default' }];    // ServiceMonitorTab.tsx:576
```

- **为什么是隐性问题**：「默认线路」这一个语义在四处有三种写法：写入端 RecordForm 用 `'0'`，服务监控绑定表单用 `'default'`，展示端 `Records.tsx:245` 必须同时兼容 `'0' | 'default' | ''` 才能正确显示。没有单一归一化点，任何一处单独改动都会让其它处失效（例如新增「无线路」语义时必然漏改）。同类「首项即默认」的隐式契约还有两处：`DomainListTab.tsx:68` 用 `accounts[0]?.id ?? 0` 把列表首项当默认账号，`Accounts.tsx:67,72` 用 `providers[0]?.type` 当默认 provider 类型；`0` 与 `''` 同时充当「未选择」哨兵。
- **影响**：① 线路下拉在非多线路场景写入 `'0'`，服务监控表单写入 `'default'`，后端必须同时识别两种；② `accounts` 是异步查询（`DomainListTab.tsx:333`），首渲染为空时 `accountId` 永久停在 `0`，新增域名对话框的账号下拉呈空值、`mode==='sync'` 永不启用，用户必须手动重选；③ 默认 provider 随服务端注册表顺序漂移。

- **级别**：P1｜**归属**：0.0.1 存量｜**置信度**：HIGH

### D-04｜P1｜`useRealtimeData` 每次渲染都重建 WebSocket

- **位置**：`client/src/hooks/useRealtimeData.ts:34-36`、`:113`、`:159-187`；调用点 `client/src/pages/Records.tsx:108-112`
- **代码摘录**：

```ts
const refreshData = useCallback(() => { queryClient.invalidateQueries({ queryKey }); }, [queryClient, queryKey]);  // 34
}, [enabled, connectWebSocket, startPolling, stopPolling, disconnectWebSocket]);                                     // 187
```

- **为什么是隐性问题**：`queryKey` 与 `websocketEventTypes` 由调用点以**内联数组字面量**传入（`Records.tsx:109-110`），每次渲染都是新引用，`refreshData` → `connectWebSocket` 的依赖链因此每次渲染都变，末尾 effect 每次渲染都会先 cleanup（`disconnectWebSocket()` + `stopPolling()`）再重连。Hook 的入参类型 `queryKey: any[]`（`:11`）本身就在鼓励传内联数组——签名表达不了「必须稳定引用」这个隐含前提。
- **影响**：Records 页每敲一个字（`keyword` state）就关闭并重开一条 WS，`onclose` 还会顺带 `startPolling()`，高频输入下形成连接风暴与服务端 WS 日志洪水；`:59,61,71,133` 的 `console.log` 每次都刷屏。另外 `:190` 返回的 `hasWsConnection` 读的是 ref 当前值，调用方永远拿到初始 `false`，任何依赖它的 UI 判定都不可信。
- **修复方向**：Hook 内部把 `queryKey`/`websocketEventTypes` 序列化成字符串作为依赖（`const key = JSON.stringify(queryKey)`），或要求调用方传入 memo 化常量并在类型上标注 `readonly string[]`；`hasWsConnection` 改为 state 返回值。
- **级别**：P1｜**归属**：后续引入（随实时刷新/WS 特性加入）｜**置信度**：HIGH

### D-05｜P1｜绕过 api 封装直接 fetch，且与 httpOnly 认证模式并存

- **位置**：`client/src/pages/Security.tsx:120-122`、`:134-140`、`:170`、`:193`、`:225`、`:246`、`:270`；`client/src/utils/rsaEncrypt.ts:18`；`client/src/components/ProviderIcon.tsx:15`；对照 `client/src/api/client.ts:17-24`
- **代码摘录**：

```ts
const response = await fetch('/api/security/sessions', {                                  // 120
  headers: { Authorization: `Bearer ${localStorage.getItem('token')}` },          // 121
```

- **为什么是隐性问题**：`api/client.ts:20-23` 明确写着「token 现在只在 httpOnly cookie 里，不需要手动加 Authorization」，而 Security.tsx 仍按旧契约从 `localStorage` 取 token 拼头。当前 localStorage 里通常没有 token，实际发出的是 `Authorization: Bearer null`——请求能通全靠 cookie 兜底；一旦服务端按「有 Authorization 头就按 Token 校验」处理，这些接口会稳定 401。同一类问题还绕过了 `baseURL`：`rsaEncrypt.ts:18` 与 `ProviderIcon.tsx:15` 硬编码 `/api/...`，在 `VITE_API_URL` 部署（`client.ts:4-6`）下必然 404。
- **影响**：安全页 7 个端点（会话列表、单条注销、全部注销、2FA 状态/初始化/启用/禁用）与登录加密公钥、provider 图标全部脱离统一客户端：无超时、无 401 兜底跳转、无 baseURL、无统一错误格式；换部署方式或换认证实现时这些点会成片失效。
- **修复方向**：新增 `api/security.ts`（`sessionsApi` / `twoFaApi`）全部走 `api.get/post/delete`；`getPublicKey` 改为 `authApi.getPublicKey()`；`ProviderIcon` 用 `api.defaults.baseURL` 拼图标地址。
- **级别**：P1｜**归属**：后续引入（httpOnly 迁移后未同步清理）｜**置信度**：HIGH

### D-06｜P1｜2FA / 会话状态「失败即正常值」

- **位置**：`client/src/pages/Security.tsx:142-161`、`:118-130`
- **代码摘录**：

```ts
let nextTotpEnabled = false;                                  // 142 安全默认值
if (totpResponse.ok) { ... }                                  // 147 非 ok 时静默跳过
} catch (error) { console.error('Failed to load 2FA status:', error); }   // 162
```

- **为什么是隐性问题**：`loadTotpStatus` 先给一组「安全默认值」（`totpEnabled=false`、`backupCodesRemaining=0`、`validationEnabled=true`），只有 `response.ok` 时才覆盖；请求失败或非 2xx 时既不清错也不提示，直接把「拿不到」渲染成「2FA 未启用」。`loadSessions` 同理：没有非 ok 分支，catch 只 `console.error`，`sessions` 保持空数组。调用方无法区分「真的没有」与「查不到」。
- **影响**：① 用户看到「2FA 未启用」可能重复绑定 TOTP，产生两套密钥；② 用户看到「无活跃会话」误以为无可注销登录，实则列表加载失败，无法处置可疑会话；③ 违反 root.ai.md §客户端架构 4「禁止静默失败」。误判发生在安全页，隐蔽性高于普通列表页。
- **修复方向**：改为三态 `{ status: 'loading' | 'ok' | 'error'; data?: T }`，失败时页面显示「状态加载失败，请重试」并给重试按钮；2FA 徽标在 error 态显示「未知」而不是「未启用」。
- **级别**：P1｜**归属**：0.0.1 存量｜**置信度**：HIGH

### D-08｜P1｜`enabled` 三套表示，同文件两处读法相反

- **位置**：`client/src/api/types.ts:59`、`:68`；`client/src/pages/Accounts.tsx:357`、`:376`；`client/src/pages/Records.tsx:63`；`client/src/pages/domains/DomainListTab.tsx:561`；`client/src/api/accounts.ts:11`、`api/domains.ts:12`
- **代码摘录**：

```ts
enabled?: boolean;                       // api/types.ts:59  DnsAccount
enabled?: number;                        // api/types.ts:68  Domain（注释：0=禁用，1 或 undefined=启用）
const currentEnabled = !!row.enabled;    // Accounts.tsx:376
```

- **为什么是隐性问题**：同一个「启用」在类型层有三种表示：`DnsAccount.enabled: boolean`、`Domain.enabled: number(0/1/undefined)`、查询参数 `enabled: 'enabled'|'disabled'|'all'`。更直接的缺陷在 Accounts.tsx 内部：`:357` 用 `row.enabled !== false` 判显示（undefined → 显示「启用」），`:376` 用 `!!row.enabled` 判当前值（undefined → 视为「禁用」）——同一行数据、相距 19 行、结论相反。
- **影响**：对 `enabled` 缺省的账号，列表显示「启用」，用户点开关时前端以为自己在「启用」，实际发 `enabled: true`（无变化，点了没反应）；反向数据则显示「禁用」却发出 true。`Domain` 侧的 `enabled === 0` 判定分散在 `Records.tsx:63` 与 `DomainListTab.tsx:561`，第三处新增时极易写成 `!d.enabled` 而把 undefined 判成禁用。
- **修复方向**：在 `api/types.ts` 收口为 `export const isEnabled = (v: boolean | number | undefined) => v !== false && v !== 0;` 作为唯一实现，两处调用都改用它，类型层统一成 boolean（api 层归一化）。
- **级别**：P1｜**归属**：0.0.1 存量｜**置信度**：HIGH

### D-09｜P1｜乐观更新写在错误的 queryKey 上（静默空操作）

- **位置**：`client/src/pages/Accounts.tsx:210`、`:296`、`:300-303`、`:321-326`
- **代码摘录**：


- **为什么是隐性问题**：真实查询键带三个过滤器后缀，而乐观更新与回滚都精确读写 `['accounts']`。`getQueryData` 是精确匹配（不是前缀匹配），因此永远返回 `undefined`，`onMutate` 的 `if (previousAccounts)` 不成立、`onSuccess` 的 `setQueryData` 写入的是一个无人订阅的幽灵缓存条目，`onError` 的回滚也是死代码。
