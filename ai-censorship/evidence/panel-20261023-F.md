## 结论

文档（docs/api.md）、契约（client/src/api 类型 + 路由签名）、模型（registry 能力位）三处存在 12 处可复现的错位，其中最危险的不是"写错字"，而是**接口接受了参数却静默丢弃**（记录 `status`、令牌服务权限）和**同一字段承载两种语义**（`line` 既是线路 ID 又是代理开关）。
`docs/api.md` 被规范定为"第一权威"，但它至少 3 处与实现相反（`/api/system/*` 鉴权、`securityPolicy` 备用路由、记录列表分页上限），按文档接入的第三方会稳定踩坑。
建议优先修 F1–F4（契约层），F8–F11（规范漂移）可批量修订，避免后续按错误清单改动。

## 逐条详情

### F1 · 创建令牌的服务权限是硬编码，文档承诺的"服务级权限"无法表达

- **位置**：`server/src/routes/tokens.ts:146`、`:149`（对照 `:333`、`:344`；`docs/api.md:10`、`docs/api.md:738`；`root.ai.md:850`、`root.ai.md:856`）
- **代码摘录**：
  ```ts
        allowed_services: ['*'], // Allow all services - token has same permissions as user
        max_role: userRole,
  ```
- **为什么是隐性问题**：`POST /api/tokens` 只解构 `{ name, allowed_domains, start_time, end_time }`（`tokens.ts:132`），然后把服务权限写死为 `['*']`、角色取创建者角色；而 `PUT /api/tokens/:id` 却接受 `allowed_services`（`tokens.ts:333`、`:344`）。同一"令牌权限"语义在两个端点各写一套：创建路径不可表达，更新路径可表达。文档侧又反过来宣称支持——`docs/api.md:10`"支持域名/服务/时间范围限制"、`root.ai.md:850`"`API Token`（程序化访问，支持域名/服务/时间范围限制）"、`root.ai.md:856`"API Token 支持细粒度权限控制（服务权限、域名权限）"。`client/src/api/types.ts:317` 的 `UserToken.allowed_services`、`:320` 的 `max_role` 也照着"可配置"建模，于是三层都以为有这个能力。
- **影响**：任何用户为 DDNS 场景创建的令牌都等于"全服务 + 自身角色"。`requireServicePermission(service)` 对这些令牌恒放行，最小权限不可实现；管理员创建的令牌直接继承管理员。安全审计按文档阅读会得出"权限已受限"的错误结论。客户端 UI 也不提供该选项（`client/src/api/tokens.ts:9-14`），所以连"想限制也限制不了"。
- **修复方向**：`POST` body 增加 `allowed_services?: string[]`（默认 `['dns']`，不再默认 `'*'`）与 `max_role`（必须 `<= 创建者角色`，超出即 422）；把"令牌权限归一化+封顶"抽成 `service/token.ts` 里一个函数，POST/PUT 共用；`docs/api.md` §18 写清默认值与封顶规则。
- **级别**：P1　**归属**：0.0.1 存量　**置信度**：HIGH

### F2 · 更新记录接受 `status` 却静默丢弃

- **位置**：`server/src/routes/records.ts:690`、`:692`（对照 `:719-723`；`docs/api.md:449`）
- **代码摘录**：
  ```ts
  const { name, type, value, line, ttl, mx, weight, remark, status, cloudflare, aliyunesa } = req.body as {
    ttl?: number; mx?: number; weight?: number; remark?: string; status?: number;
  ```
- **为什么是隐性问题**：`status` 被解构、被类型声明，但该处理器后续只做 `effectiveLine` 计算与 `updateDomainRecord(recordId, name, type, value, effectiveLine, ttl, mx, weight, remark)`（`records.ts:728`），全程没有 `setDomainRecordStatus`，也没有"忽略该字段"的日志或 400。而 `docs/api.md:439-453` 的更新示例明确带 `"status": 1`，第三方读到的是"可以更新启用状态"。
- **影响**：按文档把 `status` 放进 PUT 的调用方（DDNS-Go / acme.sh 类适配器、自研脚本）会收到 `code:0`，认为记录已启用，实际状态未变；失败被伪装成成功且无任何痕迹。前端同样能构造这种请求——`DnsRecord.status` 是必填字段（`client/src/api/types.ts:111`），`recordsApi.update` 接受 `Partial<DnsRecord>`（`client/src/api/records.ts:41`）。
- **修复方向**：二选一并保持三层一致——(a) 真正支持：在 `status !== undefined` 时调用 `setDomainRecordStatus`（provider 不支持则 422 说明），(b) 明确不支持：从 `docs/api.md` 的 PUT 示例与 `DnsRecord` 更新类型中移除，收到该字段直接 `sendError(res, 'status 请使用 PUT /records/:id/status', 400)`。不要保留"接受但丢弃"。
- **级别**：P1　**归属**：0.0.1 存量　**置信度**：HIGH

### F3 · `line` 一个字段两种语义，且写路径对任意 provider 都按 proxied 改写

- **位置**：`server/src/routes/records.ts:470-474`、`:719-723`、`:31-33`（对照 `cloudflare/adapter.ts:354,358`、`aliyunesa/adapter.ts:382`；`docs/api.md:406`、`:419-432`）
- **代码摘录**：
  ```ts
    const effectiveLine = cloudflare?.proxied !== undefined
      ? (cloudflare.proxied ? '1' : '0')
  // 读路径：
    const cloudflare = r.Cloudflare ?? (r.Proxiable !== undefined ? { proxied: r.Line === '1', ... } : null);
  ```
- **为什么是隐性问题**：`line` 在 Cloudflare/ESA 上承载"是否代理"（适配器把 `proxied` 编码成 `'1'`/`'0'`），在阿里云等厂商上是线路 ID。写路径**不看账号类型**：只要 body 里出现 `cloudflare.proxied` 或 `aliyunesa.proxied`，`line` 就被覆盖（`records.ts:470-474`、`:719-723`）；读路径只为设置了 `Proxiable` 的 provider 反推出 `cloudflare`，ESA 只写不读（`aliyunesa/adapter.ts:382` 只设 `Line`，从不设 `Proxiable`）。文档把两者并列展示、不写优先级与适用范围（`docs/api.md:424` 的 `"line": "0"` 与 `:429-430` 的 `cloudflare/aliyunesa`）。
- **影响**：给阿里云域名发 `{"line":"电信","cloudflare":{"proxied":false}}` 会被静默改成 `line='0'`——记录落到错误线路且返回成功。ESA 记录读回来 `cloudflare` 恒为 `null`，代理状态只能靠"猜 `line==='1'`"；任何按 `cloudflare.proxied` 读写的客户端在 ESA 上都会丢失该状态。这也是"同一语义没有单一归一化点"的典型：编码在 3 个适配器、解码在 1 个路由函数、文档在 2 处。
- **修复方向**：在 API 边界拆成两个字段：`line`（线路 ID，仅在 `capabilities.dns` 声明支持线路时有意义）与 `proxied`（布尔，仅在 `capabilities.dns.proxiable` 为 true 时接受）；`proxied`→`line` 的编码只留在各适配器内；路由只做"能力位校验 + 参数二选一"（同时给两者且冲突 → 400）。`docs/api.md` 与 `client/src/api/types.ts:95-115` 同步。
- **级别**：P1　**归属**：0.0.1 存量　**置信度**：HIGH

### F4 · 两个 router 同挂 /api/security，备用路由一半是死代码，文档却当成可用接口

- **位置**：`server/src/app.ts:509-510`（对照 `server/src/routes/security.ts:13,24,36,260`、`server/src/routes/securityPolicy.ts:38,80,105,164`；`docs/api.md:679-691`）
- **代码摘录**：
  ```ts
  app.use('/api/security', securityRouter);
  app.use('/api/security', securityPolicyRouter);
  ```
- **为什么是隐性问题**：两个 router 挂同一前缀且路径重叠：`GET/PUT /policy`、`POST /password-strength`、`GET /trusted-devices`。Express 按注册顺序匹配，`securityRouter` 先注册即先应答，`securityPolicy.ts` 的同名四条**永远不可达**；只有 `/2fa/requirement`（`securityPolicy.ts:137`）和 `/check-device`（`:210`）是活的。`docs/api.md:679-691` 却把整个 securityPolicy 组列为"安全策略（备用路由）"可用接口，连 `DELETE /trusted-devices/:id` 与 `DELETE /trusted-devices/:deviceId` 两种参数名都分别列了出来。
- **影响**：后续维护者（或 AI）只修改 `securityPolicy.ts` 里那份实现时——它用了 `asyncHandler`、`noTokenAuth('security policy')`、`sendSuccess` 封装，看起来"更规范"——行为零变化，等于静默失效；排查时看到的却是"代码明明改了"。swagger-jsdoc 对同一 path 产出重复定义，`/api/docs` 展示哪一份取决于合并顺序，读文档的人无法判断哪份是活的。
- **修复方向**：删除 `securityPolicy.ts` 中与 `security.ts` 重叠的 4 条路由（保留 `/2fa/requirement`、`/check-device`，或整体改挂 `/api/security-policy`）；`docs/api.md` §14 只保留一份端点表，并注明"安全相关端点唯一来源 `routes/security.ts`"。
- **级别**：P1　**归属**：0.0.1 存量　**置信度**：HIGH

### F5 · 文档两处宣称 /api/system/* 免鉴权，实现全部要求认证

- **位置**：`docs/api.md:15`、`docs/api.md:620-623`（对照 `server/src/routes/system.ts:8`、`:45`；`server/src/app.ts:459-462`）
- **代码摘录**：
  ```ts
  router.get('/info', authMiddleware, async (req: Request, res: Response) => {
  router.get('/version', authMiddleware, async (_req: Request, res: Response) => {
  ```
- **为什么是隐性问题**：`docs/api.md:15` 把 `/api/system/*` 与 `/api/init/*`、`/api/rdap/*` 并列写进"公共路由…无需鉴权"；§12 表格（`:622-623`）又逐条标"鉴权：无"。实现里 `system.ts` 只有这两个端点，**都**挂了 `authMiddleware`。叠加第二层不一致：`initCheckMiddleware` 的豁免清单只有 `/api/init` 和 `/api/rdap`（`app.ts:459-462`），所以未初始化时 `/api/system/*` 还会先被 503 拦掉——文档描述的"公开探活端点"实际有 401 与 503 两道门。
- **影响**：第三方按"第一权威"文档裸调 `/api/system/version` 做部署探活，得到 401（或未初始化时 503），会被误判为"部署/BFF 鉴权配置坏了"；运维也可能因为文档把 /api/system 当公开前缀而把它放进反代的免鉴权白名单，形成预期外的暴露面评估错误。
- **修复方向**：以代码为准修文档（这两条端点的鉴权写 `authMiddleware`，并注明受 `initCheckMiddleware` 约束）；如果业务上确实需要公开探活，则新增一个最小化的 `GET /api/system/ping`（脱敏、无版本细节）并同时加入豁免清单——但不要用现有的 `/version`（它返回 deployMode 与 logLevel，见 `system.ts:64-71`）。
- **级别**：P1　**归属**：0.0.1 存量　**置信度**：HIGH

### F6 · RDAP 限流的"已认证免限流"实现为"有 Bearer 头就免限流"

- **位置**：`server/src/middleware/rateLimit.ts:94-99`（对照 `docs/api.md:512-528`；`server/src/routes/rdap.ts` 全文无鉴权代码）
- **代码摘录**：
  ```ts
    const hasBearerToken = req.headers.authorization?.startsWith('Bearer ');
    return hasSessionCookie || !!hasBearerToken;
  ```
- **为什么是隐性问题**：`skip` 用"请求头存在"代替"认证成功"。`docs/api.md:515` 的表格把这条写成"**已认证**（Bearer token 或 session cookie）→ 不限速"，读起来是"登录用户的特权"；它下面引用的代码片段（`:517-528`）其实已经是"只看头"。而 `rdap.ts` 根本不解析 `Authorization`（全文 grep 无命中），所以伪造 `Bearer x` 的匿名请求会同时获得两件事：跳过 2 req/s 限流，且照常拿到未认证的完整 RDAP 结果。
- **影响**：任何人都能用一行 `-H 'Authorization: Bearer x'` 对公开 RDAP 端点做无限并发；该端点会向多个上游 RDAP/WHOIS 源并发查询（`docs/api.md:558-564` 描述的分层竞速），等于把项目当作免费放大器，同时把上游封禁风险转嫁给服务器 IP。
- **修复方向**：`skip` 改为"校验通过才跳过"——复用只读的 token/JWT 校验（校验失败仍走限流），或对匿名与"头无效"统一限流、只对有效凭证提额；`docs/api.md` §11 表格措辞改为"携带**有效**凭证"，并把"无效头等同匿名"写进文档。
- **级别**：P1　**归属**：0.0.1 存量　**置信度**：HIGH（代码事实确定；实际滥用面取决于该端点对外暴露程度）

### F7 · /api/init/status 把探测失败伪装成"未初始化"，客户端类型还丢了一个字段

- **位置**：`server/src/routes/init.ts:106-118`（对照 `:98-103`；`client/src/api/init.ts:17`；`client/src/pages/Login.tsx:24-28`；`root.ai.md:481-486`）
- **代码摘录**：
  ```ts
      // 探测失败时按最保守结果返回，且明确标记数据库不可达
        initialized: false,
        dbInitialized: false,
  ```
- **为什么是隐性问题**：成功路径返回四个字段（含 `dbReachable`，`init.ts:102`），失败路径把 `initialized` 直接压成 `false` 并仍然 `code:0`。这与 `root.ai.md:481-486` 的三态口径（`unreachable` 绝不等同 `uninitialized`、失败不得降级成"正常值"）冲突：正常路径用粘性标记 `isSystemInitialized()`，失败路径却绕过了它。同时 `client/src/api/init.ts:17` 的类型只声明 `{ initialized, dbInitialized, hasUsers }`，服务端下发的 `dbReachable` 在类型层被吞掉，消费方无从区分"故障"与"首次部署"。
