1. **门禁存在结构性假绿**：Test Suite 的汇总作业漏判 `lint-and-build` 与 `e2e-test`，`test-database` 六项检查中四项失败被 `continue-on-error` / `|| true` 折叠，server 覆盖率上传指向一个永不生成的文件——三条链都能在真实失败时打出绿色结论。

### H-01 · 环境校验是死代码，生产不设 JWT_SECRET 也照样启动

- **位置**：`server/src/config/env.ts:104`（`validateEnv`）、`:137`（`getDbConfig`）、`:146`（唯一调用点）、`server/src/app.ts:3`、`server/src/service/jwt.ts:12-23`、`docker-compose.yml:12-15`
- **代码摘录**：

```ts
// env.ts:104 / :146 —— validateEnv 唯一的调用点位于 getDbConfig() 内部
export function validateEnv(): void { ...    validateEnv();
```

```ts
// jwt.ts:20-23
const generatedSecret = crypto.randomBytes(32).toString('hex');
log.warn('JWT_SECRET not set, using randomly generated secret.');
```

- **为什么是隐性问题**：`grep -rn 'getDbConfig' server/src` 只有定义没有调用点（`app.ts` 只 import 了 `loadEnv`）。于是规范 `环境配置 3「生产环境强制检查 JWT_SECRET 强度」「MySQL/PostgreSQL 配置验证必需的连接参数」两条强制条款，**实现存在、执行路径不存在**。而 `jwt.ts:12-16` 只覆盖「已设置但过短」，未设置时走 `:20-23` 的随机密钥分支——生产不拦截、不退出。`docker-compose.yml` 正是「不设置」的典型部署：`environment` 只有 `NODE_ENV/PORT/DATA_DIR`，没有 `JWT_SECRET`。
- **影响**：按仓库自带 compose 部署，每次重启 `BASE_JWT_SECRET` 变化 → 全部已签发 JWT 立即失效（表现为"随机掉登录"，无错误日志）；`DB_PASSWORD` 缺失也不会被拦在启动前，而是带空密码连库。`env.ts` 里 `errors` 收集逻辑整体成为不可达代码。
- **修复方向**：在 `app.ts` 启动序列（连库之前）无条件调用 `validateEnv()`；把「生产未设置 JWT_SECRET」从 warn 升级为硬失败（或要求显式 `HIDNS_ALLOW_EPHEMERAL_JWT=true` 才放行）；compose 增加 `JWT_SECRET: ${JWT_SECRET:?JWT_SECRET required}`；把 DB 必填参数校验与 `db/dal/config.ts` 的默认值合并为单点。
- **级别**：P1（若把「生产强制检查」视为安全边界，应按 `代码审核团 2 升为 P0）
- **归属**：0.0.1 存量（`env.ts` 最后一次改动为 641ffd8/2026-06-10；调用方消失的具体提交标「待核实」）
- **置信**：HIGH（零调用点已 grep 核实；随机密钥分支已读源码核实）

### H-02 · `Test Summary` 漏判 lint 与 E2E，失败可以打印 "All tests passed!"

- **位置**：`.github/workflows/test-suite.yml:335-365`（`needs` 在 338，判定在 355-364）
- **代码摘录**：

```yaml
needs: [lint-and-build, unit-test-server, unit-test-client, test-sqlite, test-postgresql, test-mysql, e2e-test]   # :338
if [[ "${{ needs.unit-test-server.result }}" == "failure" ]] || \   # :357 判定链只有这 5 个 job
   ... [[ "${{ needs.test-mysql.result }}" == "failure" ]]; then ... echo "All tests passed!"   # :361-364
```

- **为什么是隐性问题**：汇总作业把 `lint-and-build` 与 `e2e-test` 列进 `needs` 并在摘要表里展示，但 `Check for failures` 只枚举了五项（server/client 单测 + 三种数据库），恰好漏掉 lint/类型检查与 E2E。更隐蔽的是级联效应：`unit-test-*`、`test-*` 全部 `needs: lint-and-build`，lint 或 build 失败时它们的结果是 `skipped` 而非 `failure`，判定条件全为假。
- **影响**：lint 失败 / 类型检查失败 / E2E 全红时，这一步依然 `echo "All tests passed!"` 并 exit 0。若仓库把 "Test Summary" 配成 required check（这正是它的命名意图），违规变更可直接合入；即便没配，reviewer 依据这一步的结论也会被误导。
- **修复方向**：判定改为遍历 `needs` 全部结果，除 `success`/`skipped` 外一律失败（或 `if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')`）；摘要表与判定共用同一份 job 清单，避免两处枚举。
- **级别**：P1
- **归属**：0.0.1 存量（dc0ce6d/2026-04-24 引入）
- **置信**：HIGH（脚本全文已读；依赖失败时 `needs.<job>.result` 为 `skipped` 属 GitHub 既定语义）


- **为什么是隐性问题**：`init-fresh`、`test-basic`、`test-persistence`、`test-no-env`、`test-recovery` 五步都带 `continue-on-error: true`，而收口的 `Check Critical Tests` 只判前两项。`test-no-env` 还叠加了 `|| true`——该步 `outcome` 永远是 `success`，连摘要表（`:175`）都在展示一个不可能失败的检查。注释（`:119-120`）说明作者已知"加容错后 step outcome 恒 success"，却没处理同一文件里 `:135`+`:140` 这对组合。

### H-05 · server 覆盖率的源文件从不生成，上传步骤静默

- **位置**：`.github/workflows/test-suite.yml:155-169`；`server/package.json:13,16`；`server/vitest.config.ts:8-18`
- **代码摘录**：

```yaml
run: pnpm --filter dnsmgr-server run test                  # :156 —— vitest run，无 --coverage
files: ./server/coverage/lcov.info                         # :166
```

- **为什么是隐性问题**：`vitest` 只有在传 `--coverage`（或配置 `coverage.enabled: true`）时才产出覆盖率；`server/vitest.config.ts` 只声明了 `coverage.reporter`，没有 `enabled`。所以 `server/coverage/lcov.info` 在整个作业生命周期内不存在。包内明明有 `test:coverage` 脚本（`:16`）却无人调用——同一件事两套入口，CI 走的是不产覆盖率的那条。
- **影响**：覆盖率门禁形同虚设；因 `fail_ci_if_error` 未显式设为 `true`（codecov-action v5 的默认值离线无法核实，标「待核实」），上传失败不会让作业变红，形成"有覆盖率面板但数据永停旧值或为空"的假象。client 侧（`:207`）传了 `--coverage`，两侧口径不一致，容易被误读为"server 覆盖率未变"。
- **修复方向**：`unit-test-server` 改用 `pnpm --filter dnsmgr-server run test:coverage`；`codecov-action` 显式 `fail_ci_if_error: true`，或在上传前加 `test -f server/coverage/lcov.info` 断言。
- **级别**：P1
- **归属**：0.0.1 存量
- **置信**：HIGH（"文件不生成"为 HIGH；codecov 默认值语义为 MEDIUM-待核实）

### H-06 · 门禁的"声明面"与"执行面"不一致（pr-checks 承诺六项、实跑一项；commit-checks 四步只 echo）

- **位置**：`.github/workflows/pr-checks.yml:173-199`（承诺文案）、`:53-162`（实际作业）；`commit-checks.yml:133-158,176-197`；`.github/workflows/test-suite.yml:17-32`（触发过滤）
- **代码摘录**：

```yaml
- ✅ 单元测试 / - ✅ 集成测试 (SQLite/PostgreSQL/MySQL) / - ✅ E2E测试 / - ✅ 安全审计   # pr-checks.yml:180-183
if [ $FOUND -eq 1 ]; then echo "请检查上述文件是否包含敏感信息"   # commit-checks.yml:195-197，不 exit
```

- **为什么是隐性问题**：`pr-checks.yml` 的 job 只有 `pr-info / pr-validation / code-changes / dependency-check / auto-comment / merge-check / summary`，唯一会失败的实质检查是 `pnpm audit`；机器人在每个新 PR 上自动评论宣称单测、三种数据库集成测试、E2E、安全审计"将会运行"。这些检查确实存在，但由 `test-suite.yml` 提供，而它的 `pull_request.branches` 只列 `main/master/develop/release/**`、`paths-ignore` 又排掉 `**.md` 与 `docs/**`——对非清单 base 分支的 PR 或纯文档 PR，机器人承诺的六项一项都不会发生。`commit-checks.yml` 侧同理：`Check File Size`、`Check File Encoding`、`Check Trailing Whitespace`、`Check for Sensitive Patterns` 四步只打印警告，没有任何 `exit 1`，作业永远绿，最后一项还挂着"安全检查"的名字。
- **影响**：reviewer 与外部贡献者依据机器人评论判断"检查已覆盖"，实际覆盖面取决于 base 分支与文件类型；四个卫生项无任何强制力。这是"门禁看起来存在、违规不会变红"的典型形态。
- **修复方向**：让 pr-checks 只评论它真正会跑的东西（或改为汇总 test-suite 的结论）；把四步 `echo` 改为 `exit 1`（或明确降级为 `::notice` 并从"检查"改名）；`test-suite.yml` 的 `pull_request.branches` 去掉 base 过滤，文档类 PR 用 `paths-ignore` 保留。
- **级别**：P1
- **归属**：0.0.1 存量（dc0ce6d/2026-04-24 引入）
- **置信**：HIGH（作业清单、步骤、触发条件均已逐行核实）

### H-08 · 发布不校验「版本号 ↔ 三个 package.json ↔ tag」，checkout 不固定到 tag

- **位置**：`.github/workflows/release.yml:141-151`（`Get version`）、`:84-85` 等 checkout、`:1141-1156`（Create Release）
- **代码摘录**：

```yaml

```

- **为什么是隐性问题**：规范 `发布步骤 3 要求"修改根目录、`server/`、`client/` 三个 `package.json` 的 `version`"，步骤 5 要求"打 Tag `vX.Y.Z`"，步骤 7 要求"手动触发 `release.yml`，传入版本号"。当前实现在三层都没有执行点：(a) `prepare` 只读根 `package.json`，从不读 server/client 的两个；(b) 手输版本与根版本不一致时以输入为准，而产物里被拷进包的 `server/package.json`（`:200`/`:355` 等）仍是旧版本；(c) 没有任何 `git tag` 存在性校验，`checkout` 也没有 `ref: v$VERSION`，而 `softprops/action-gh-release` 在 tag 不存在时会按 `target_commitish`（缺省默认分支）新建 tag——规范里"先打 tag 再发版"变成可选步骤。

- **级别**：P1
- **归属**：后续引入（cadee06/2026-10-21 的发版门禁只做了产物、没做版本三元组）
- **置信**：HIGH（源码行已核实；"tag 不存在则由 action 新建"依据 action 文档语义，机制相关）

### H-09 · 发布产物 ≠ 门禁验证过的依赖树；镜像运行时版本未固定

- **位置**：`.github/workflows/release.yml:177,255,333,405,478,551,620,655,689,723`（10 处）；`Dockerfile:2,8,23,54`；对照 `test-suite.yml:93`、`release.yml:98`、根 `package.json:7-9`、`release.yml:66-71`
- **代码摘录**：

```Dockerfile
FROM node:24-alpine AS builder
RUN npm install -g pnpm ; ... RUN pnpm install --no-frozen-lockfile
```

- **为什么是隐性问题**：门禁（`gate`）用 `pnpm install --frozen-lockfile`（`:98`），发布构建的十个作业却全部用 `--no-frozen-lockfile`——同一件事两套安装语义：lockfile 与 `package.json` 不一致时，门禁失败或按锁树安装，而产物作业会现场改写依赖树并照样打包。Docker 侧更彻底：`npm install -g pnpm` 不锁版本（CI 固定 `pnpm/action-setup version: 10`），基础镜像 `node:24-alpine` 是浮动标签；而 869ebe3 已把 `NODE_SEA_VERSION`、全部 workflow 的 `node-version`、`engines.node` 统一到 `>=24.22.1`（安全下限，注释 `:66-71` 列出四个 CVE），唯独没改 Dockerfile。
- **影响**：发布包与镜像里的依赖/pnpm 版本可以偏离门禁验证的那一份；`node:24-alpine` 可能解析到 <24.22.1 的补丁级（24.0–24.21 区间），容器运行时正好落在被点名的 CVE 范围内，而"发布产物运行时已升级"的结论只对 SEA/启动包成立。构建不可复现，出问题无法用 commit 复现环境。
- **修复方向**：发布构建统一改 `--frozen-lockfile`（与 gate 同口径）；Dockerfile 固定 `FROM node:24.22.1-alpine`、`RUN npm i -g pnpm@10`；再加一步 `node -e` 断言 `process.versions.node` 不低于安全下限（复用 `server/scripts/lib/node-version.mjs` 的判定）。
- **级别**：P1
- **归属**：后续引入（869ebe3/2026-10-22 升级安全基线时漏掉 Dockerfile；`--no-frozen-lockfile` 为 0.0.1 存量）
- **置信**：HIGH（10 处 + Dockerfile 三处均 grep 核实；`git show --stat 869ebe3` 确认未包含 Dockerfile）
