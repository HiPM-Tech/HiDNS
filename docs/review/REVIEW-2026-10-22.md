## 一、结论摘要

### P0 · 必须先修（功能已静默失效）

1. **`pages/Security.tsx` 的 8 处裸 `fetch` 全部携带 `Bearer null`。** [FACT]
   该文件用 `Authorization: Bearer ${localStorage.getItem('token')}`（`:121/135/139` 等），
   而全仓 `localStorage.setItem('token')` **零命中** —— 鉴权早已改为 httpOnly cookie（`api/client.ts:17-24`）。
   失败分支只有 `if (response.ok)`，不 ok 就什么都不做，于是**会话管理、2FA 状态、passkey 列表三块功能静默失效**。
   其中 `/api/security/sessions`、`/api/security/sessions/:id`、`/api/security/sessions/logout-others` 三个路径**服务端根本不存在**；
   `/api/security/2fa/status` 真实路径是 `/2fa-status`（`security.ts:80`）；
   `/api/webauthn/credentials` 真实路径是 `/api/auth/webauthn/credentials`（`app.ts:515`）。

2. **`GET /api/domains/whois` 被 `GET /:id` 吞掉，端点实际不可用。** [FACT]
   `domains.ts:594` 注册 `/:id`，`domains.ts:1471` 才注册 `/whois` —— `Number('whois')` 为 `NaN`，请求落到「Domain not found」。
   同文件 `:481-489` 的注释自己写着「静态路由必须定义在 `/:id` 之前」，`/renewable-domains` 遵守了，`/whois` 没有。
   该端点已在 `docs/api.md:369` 对外文档化。

3. **`securityPolicy.ts` 的三条路由被 `security.ts` 完全遮蔽，永远不可达。** [FACT]
   `app.ts:509-510` 的挂载顺序决定：`/policy`、`/password-strength`、`/trusted-devices` 全被前面的同名路由抢先匹配。

### P1 · 契约与一致性（外部客户端可能踩到）

4. **响应信封没有单一实现：3 套封装 + 4 套 `code` 口径。** [FACT]
   `utils/http.ts:69,77`（`{code,data,msg}`）、`utils/response.ts:23,35`（`{code,msg,data,timestamp}`）、
   `middleware/errorHandler.ts:51-52` 兜底用 **`message` 而不是 `msg`**；`utils/response.ts:154` 的 `globalErrorHandler` 从未注册（死代码）。
   `code` 取值同时存在 `0/1`、`-1/-2/-3`、HTTP 码（400/403/404/500）三种语义。规范只要求 `code !== 0`，所以四种都「合法」，但无法互操作。

5. **134 处 `sendError` 未传状态码 → 对外的 HTTP 状态是 200。** [FACT，lead 复核]
   `utils/http.ts:77-83` 的默认分支把 `statusCode` 定为 200，`code` 落成 `-1`。
   含义：「账号不存在」「无权限」对外都是 **HTTP 200**。外部客户端若按状态码判断会全部走成功分支。
   （三位成员口径分别为 145 / 134，差异来自多行调用的统计方式；量级一致。）

6. **130 处裸 `res.json/res.send` 绕过封装**，共 340 处 JSON 响应体里 261 处手写 `{code,msg}`、79 处是别的形态（`{error}` 32、`{success,error}` 13、其他 34）。[FACT]

7. **429 不是 JSON。** 限流器只配字符串 `message`（`rateLimit.ts:12,30,46,58,91`），express-rate-limit 走 `response.send(message)` → `text/html`。[FACT]

8. **同一语义 2–4 种码**：不存在 = 404 或 200/`-1`；无权限 = 403 或 200/`-1`；校验 = 400 或 422（仅 workflows）；上游失败 = 502（仅 workflows）或 200/`-1`。[FACT]

9. **分页 4 种结构、3 套默认值（20/50/100）、2 处无上限**，且与 `docs/api.md` 不一致：[FACT]
   域名列表代码默认 20（`domains.ts:187`）／文档写 50；记录列表代码默认 100 且**无上限、`NaN` 直接透传**（`records.ts:191-199`）／文档写 20。

### P1 · 外部兼容（DDNS-Go）

10. **四个端点齐全、路径与方法正确、API Token 可用、IDN 有 `display_name`。** [FACT] 但：
    **`subdomain` 是透传给上游的语义，服务端不做二次精确匹配**（`records.ts:196-202`）。
    阿里云映射成 `RRKeyWord`（模糊包含，`aliyun/adapter.ts:96-101`），`subdomain=www` 会命中 `www`/`www2`/`awww`。
    DDNS 客户端「查到就更新」可能改写错记录 —— 这是**唯一可能导致 DDNS 断服**的一条。[INFERENCE，依据上游语义]

11. **`docs/api-reference.md` 与实现大面积不一致**（`host` vs `name`、`priority` vs `mx`、`PATCH .../status`+`{enabled}` vs 实际 `PUT .../status`+`{status}`）。
    按 `root.ai.md:779`「api.md 为第一权威、改动须同步」的口径，这已构成「未完成」。

### P2 · 结构性

12. **没有共享层**：`RecordType`、`RoleLevel/ROLE_*`、根域解析三处前后端各一份，靠注释「保持同步」约束，无编译期保证。
13. **服务端 48 条路由前端零调用**（MCP/外部集成 14、审计 6、绕过 api 层 6、确实无消费方 22）；**api 层另有 20 个方法零调用点**，其中 failover 一组 7 个方法服务端根本不存在。

## 二、接口方向（怎么统一）

目标：让「外部客户端按 `code !== 0` 判断」与「内部按 HTTP 状态码排查」两套用法同时成立，且不再有第二套信封。

| # | 动作 | 落点 |
|---|---|---|
| 1 | **收敛为单一信封**：保留 `{code,data,msg}`，把 `utils/response.ts` 与 `errorHandler` 的 `message` 迁到 `msg`，删除未注册的 `globalErrorHandler` | `utils/http.ts` |
| 2 | **`sendError` 取消默认 200**：状态码改为必填，杜绝「错误却回 200」；`code` 语义定为**业务码**（0 成功，非 0 失败），HTTP 状态码独立表达传输层结果 | `utils/http.ts:77` |
| 3 | **建立「语义 → 状态码」唯一映射**并要求所有路由遵守：不存在 404 / 无权限 403 / 参数 400（workflows 的 422 收敛为 400，或全仓统一 422）/ 上游 502 / 频控 429 | `docs/api-error-codes.md` + 路由 |
| 4 | **限流器改用 JSON handler**，让 429 也返回信封 | `middleware/rateLimit.ts` |
| 5 | **分页契约统一**：`page`(≥1) / `pageSize`(默认 20，上限 100，强制钳制且拒绝 `NaN`) / 返回 `{items,total,page,pageSize}` | 全部分页端点 |
| 6 | **错误信息脱敏**：99 处直接回显 `error.message`/`getError()` 含 DB 与厂商报文；路由自己 catch 的分支绕过了 `errorHandler.ts:93` 的 `NODE_ENV` 保护 | 路由 catch 分支 |
| 7 | **协议类端点登记白名单**（MCP OAuth / RDAP 等形态差异有据），不是「修掉」而是「声明例外」 | 文档 + 守卫 |

## 三、抽离方向（怎么减耦合）

| # | 方向 | 内容 |
|---|---|---|
| 1 | **建 `packages/shared`**（workspace 已有 3 个包，成本低） | `RecordType`/`ValueType`、`RoleLevel`/`ROLE_*`/`isAdmin`、`getRootDomain`/`SPECIAL_SUFFIXES`、`ApiResponse<T>`、provider 配置字段、workflow action meta |
| 2 | **不共享** | ORM 行类型（`Domain`/`DnsAccount` 带库字段）；前端 `api/types.ts` 的裁剪视图是正确的，不要合并 |
| 3 | **前后端接口面对照固化为 CI 守卫** | 扫前端 `api.<verb>('<path>')` ∪ 服务端挂载表+router，断言「前端 ⊆ 服务端」，失败打印差集 |
| 4 | **禁止裸 `fetch('/api` 守卫** | 一次性归零 `Security.tsx` 那类绕过；第三方域名白名单 |
| 5 | **api 模块归位** | 新增 `api/providers.ts`、`api/security.ts`（给 8 处裸 fetch 一个家）；`tunnelsApi` 从 `accounts.ts` 拆出；`email-templates` 从 `records.ts` 拆出；删除 failover 7 个死方法 |
| 6 | **修路由顺序** | `/whois` 前移到 `/:id` 之前；`security.ts` 与 `securityPolicy.ts` 合并或改名消除遮蔽 |

## 四、整改优先级

| 批次 | 内容 | 理由 |
|---|---|---|
| **第 1 批（本周）** | P0-1 `Security.tsx` 改走 api 层并修正 3 个路径；P0-2 `/whois` 前移；P0-3 消除 `securityPolicy` 遮蔽 | 都是「功能已经坏了但没人发现」，改动小、收益直接 |
| **第 2 批** | `sendError` 状态码必填 + 429 返回 JSON + 语义→状态码映射 | 影响所有外部客户端，但需要全仓扫一遍 134 处调用 |
| **第 3 批** | 分页契约统一 + 错误信息脱敏 | 需要逐个端点改，可与功能迭代合并 |
| **第 4 批** | `packages/shared` + 两条 CI 守卫 | 结构性投入，一次性消除「靠注释保持同步」 |
| **持续** | 第二份文档 `docs/api-reference.md` 的处置（合并进 `api.md` 或明确废弃） | 两份文档都在，读者无法判断哪份权威 |

## 五、外部兼容性专项结论（DDNS-Go）

- **可以继续用**：四个端点、Token 鉴权、幂等流程（findDomain → findRecord → update/create）在结构上完整。
- **必须知道的两个坑**：① `subdomain` 在上游是模糊匹配，服务端不做精确过滤；② 记录列表 `pageSize` 无上限。
- **建议**：在 `docs/api.md` 明确写出「`subdomain` 为上游语义，可能返回包含匹配」并把 `pageSize` 钳制到 100 —— 这两条对 DDNS 客户端是契约级信息。
- [UNVERIFIED] 未启动服务、未用真实 DDNS-Go 联调；未验证各厂商对越界 `pageSize` 的实际反应。
